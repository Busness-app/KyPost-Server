# Backend

## Purpose

Go module owning the email classification engine, HTTP API server, IMAP integration, Ollama integration, polling loop, configuration, state persistence, health tracking, logging, PII redaction, and the internal receiving/permanent-mailbox foundation.

## Ownership

All code under `backend/`. Produces the `kypost-server` binary consumed by the container at runtime.

## Local Contracts

- Container-local `apply-setup --file <private-file|->` runs as the runtime data owner after base bootstrap; version1 bundles verify retained effective pairing authority and create only missing SSO/domain/recovery settings, refuse conflicts and restore holds, and audit changes through the instance store. `setup-status` reports advisory local configuration checks and external acceptance still required, without mail submission or DNS refresh. Read [installer contract](../docs/INSTALLER_SETUP.md); never equate successful configuration with production readiness.

- `receiving cloudflare route|pickup` is a one-message manual qualification profile using a separate `cloudflare-worker` ingress namespace. Compare the locally retained route file and current immutable owner/source/signed revision under fresh domain/access fences before binding; recheck after scan. Require Rspamd, verified bounded read-only HTTPS pickup and a dedicated private token file. Fixed scanner settings disable unavailable peer-authentication groups; sender MIME cannot select policy. Daemon import handles both gateway namespaces; completed replay rechecks authority without acquiring an acknowledged lease. Provider deletion is absent. Read [pilot contract](../docs/CLOUDFLARE_RECEIVING.md).
- Continuous Cloudflare receiving (`app/receiving_cfcontinuous.go`, gateway `cloudflare-continuous`) runs in the daemon only when `KYPOST_CLOUDFLARE_RECEIVING_ORIGIN` is set, beside native receiving and Rspamd and never beside the bundled receiver. It binds through the shared `bindExpected` with the owner and generation frozen in the locally recorded table revision, quarantines a mismatch or unknown revision with bytes, files a reject verdict to Junk (verdict durable in the ledger before Accept), and deletes the provider copy only once the ingress store holds the delivery archived or quarantined. A fenced host (no live marker) makes no Worker request; a 401 fences only after the credential-lock recheck. Transiently refused keys back off in memory (1 min to 1 h); a message over its mailbox's per-message limit (`errMailboxMessageLimit`) quarantines; only a full receiving store (`errCFStop`) stops fetching. A revision this instance never recorded quarantines unresolved (empty owner); `sso.ReleaseQuarantined(..., reviewedMailbox)` is the only path that binds such a delivery, to the address's current owner and only while that owner's mailbox equals the one the administrator reviewed (checked before and under the fences), never inferred from equal generations. `receiving cloudflare init|rotate|takeover --confirm move-receiving-here|status` is the operator CLI; `GET /api/admin/receiving/cloudflare` the status. Read [continuous receiving](../docs/CLOUDFLARE_CONTINUOUS_RECEIVING.md#kypost-implementation) and [cfreceiving](internal/cfreceiving/AGENTS.md).
- Quarantine release ([contract](../docs/NATIVE_PROVISIONING.md#quarantine-release)): `sso.ReleaseQuarantined` is the one release path for the admin API and `receiving quarantine release` CLI. It opens each frozen owner's mailbox as `importDelivery` does, then under `WithNativeMailAccess` (directory → users; no domain fence, no fresh DNS) requires each frozen mailbox admitted with the same owner and source, and calls `ingress.Store.Release`. It never checks or follows the address generation and never resolves an address's current owner. Refusals are `ErrQuarantineInactive` when the ledger records a durable reason (`mailboxRetired`: mailbox gone or another owner, administrator-disabled, or its primary-kind address not active) and `ErrQuarantineUnadmitted` otherwise, both wrapping `ErrQuarantineRelease` (409); never word a transient refusal as a reason to discard. Discard is `ingress.Store.Discard` and reports `discarded` or `partially_released`. Both refuse a restore hold. Path and argv gateway/IDs pass `ingress.ValidIdentifier` before lookup or logging. The CLI refuses unless the effective UID owns `STATE_DIR`, logs actor `cli:<uid>` to its terminal only (no application log files), and its step-up is `--confirm <id>`: shell access as the runtime user already reaches every credential the API step-up checks. List output (`sso.QuarantinedDeliveries`, one ledger read per call) is envelope only; never add subject, headers or body. The envelope sender is attacker-controlled: the admin UI must render every listed field as plain text.
- Sender blocks ([contract](../docs/NATIVE_PROVISIONING.md#sender-blocks)): `ingress.Blocks` (`STATE_DIR/receiving/sender-blocks.json`) is the one list for both profiles. Maddy `bind` first refuses senders outside `cfreceiving.ValidSender` (exit 7, `550 5.1.7`; the Worker refuses the same), then exits 8 (`451`) on an unreadable list and 6 (`550 5.7.1`) on a block; hosted pickup (`bindExpected`) never checks it, because the gateway already accepted that mail. `cfLoop.blockedSenders` signs blocks in force into the table; blocks are ordered manual-then-newest and cut by `cfreceiving.FitBlocks`, so they never stop routes; an unreadable list publishes routes with `DB.InstalledBlocks` (never stop routes: the Worker refuses all mail at 14 days) and reports `error`; `cfChangeMark` watches the list beside the address ledger. API (`handleSenderBlock*`, `nativeDomainGate`) and CLI (`receiving blocks`, `--confirm <value>`, STATE_DIR owner) pass the configured domain set as `own`; audits carry `ingress.BlockID` whenever the value normalizes, never the value. Mail-domain add/re-add (`refuseBlockedDomain`) is 409 while a block matches the domain or an address on it. Automatic blocks ([contract](../docs/NATIVE_PROVISIONING.md#automatic-sender-blocks)): `accept` passes the scan's `ingress.Authentication` to `senderEvidence` after a reject verdict (`Evidence.Reject` with the configured domains as `own`, audit by block ID, `block_level`, `until_ms`) and after a commit (`Evidence.Accepted`, authenticated domains only); it runs with its own 2-second deadline (`evidenceTimeout`), drops work on contention and never changes the SMTP answer. Block list API/CLI include `Evidence.Status`; unblock answers success with a `warning` on `ErrUnblockNotRecorded`; the CLI audits with the API's action names. `scanReceivingSpam` fills `Authentication` only for direct SMTP, from exactly `R_SPF_ALLOW` and `R_DKIM_ALLOW`'s `d=` plus the single From mailbox (`receivingAuthentication`); hosted scans return none, so Cloudflare never feeds evidence.
- `importDelivery` quarantines a pending delivery after an import refusal (other than `ErrRoute` and `ErrNativeRestoreHold`) when, under the directory lock, the ledger shows a frozen address moved, not `active` or at another generation (`quarantineRetired`). Generations change only through durable decisions (mailbox disable, release/reassign, directory deactivation, promotion, domain retirement), so directory lag, storage, lock or sign-on configuration failures and local `users` deactivation leave the delivery pending. Do not key this on error identities: `ErrNativeProvisioning` mixes durable and transient causes.

- `KYPOST_RECEIVING_RSPAMD` is strict opt-in and scans only newly staged native DATA before `holding.Accept`, outside authority fences. The fixed local HTTP transport is bounded and refuses invalid/unavailable verdicts; recheck frozen authority after scan. Exact accepted replay keeps existing sender/digest/authority checks without scanner dependence. Receiver-supplied IP/HELO are command arguments only with the feature enabled; HELO is not authenticated. No verdict/header rewrite, Junk move or client API change. See [spam setup](../docs/RECEIVING_SETUP.md#optional-rspamd-sidecar).

- Offline `LifecycleStore.FenceRestoredNativeTokens` runs only in exclusive stopped staging, validates the usable epoch and complete native snapshot under its existing lifecycle fence, then raises the existing `RevokedBefore` of every ledger account with a source (published in users.json or not) to at least current Unix time plus 31. Preserve higher floors, all other lifecycle metadata and legacy entries. Missing authority/write failure refuses; it grants no current authority or hold release.
- `sso.NativeRestoreQualificationFile` is written only by offline quarantine and read only by `CheckNativeRestoreQualification`, which reports every unmet release precondition (marker, epoch, ledger mailbox generations, queued/retryable outbox) without mutating. See [backup](internal/backup/AGENTS.md).
- `sso.NativeRestoreReleaseStatus` (API `GET /api/admin/native-recovery/status`, CLI `restore status`) changes no state and takes no locks, lock files, key generation or DNS; SQLite may create -shm/-wal companions beside mailbox databases, so the CLI runs as the `STATE_DIR` owner. Lock-free reads can mix two moments: status is advisory and the release re-checks under fences. It returns reasons, never evidence, digests or nonces. It reuses the checks a release must reuse so the two cannot disagree: `completedRepairReasons` (P1 journal/evidence/window, P2 current digest/barriers/ownership; `openRepairReasons` gates `CompleteNativeRecoveryRepairHeld`, both wrap `repairReasons`), `CheckNativeRestoreQualification` (P3), `nativeRestoreTokenFenceReasons` (P7) and `errNativeRecoveryNoSubjects` (P9). P4–P6 and P8 (last recorded domain proofs) are reported as checked at release. After a release it reports `released` and `resyncSubjects` (active floors without a newer directory revision).

- Held native accounts cannot authenticate with local/derived passwords, outstanding MFA challenges, SSO callbacks/step-up, existing cookies or QR key-exchange tokens. Shared session grant/current-user admission and early credential checks use either private native marker, independently of feature flags; preserve durable TOTP/recovery material and QR nonces on refusal. Keep an independently provisioned legacy recovery admin available. Offline hold staging requires stopped services; already admitted operations are not canceled. Only the flagged hold release below removes the hold.

- Held native recovery uses protected admin challenge/evidence POST routes with exact-action confirmation, approved connection/current pairing-key fingerprint and strict 384 KiB wrapper/256 KiB decoded evidence. Settings → directory → fresh users → session fences recheck administrator witnesses and expiry before committing. Persist separate exact evidence and one-use consumption atomically. Evidence imports install revision barriers only for native reservations without any local account matching owner ID or subject; published native/legacy accounts continue ordinary offboarding/demotion until a separate verified repair intent. Prior published barriers require a strictly newer durable directory revision unless exact historical native repair provenance binds issuer/subject/mailbox/source and floor. Barriers precede replay acknowledgement and never weaken on expiry/invalidation. Evidence import does not mutate directory/account state. The private `NativeSendEpoch` now tracks authority changes for all existing users, including local recovery admins; retain its persisted field name. Offline restore staging is exclusive, never concurrent with API writes. A separately confirmed held repair route is available; release is separate. See [consumer contract](../docs/NATIVE_RESTORE_AUTHORITY.md#protected-consumer-procedure).

- Release floors ([design](../docs/NATIVE_RESTORE_RELEASE.md)): `lifecycleFile.ReleaseFloors` is separate from `RecoveryFloors` and only ever raised (`RecordNativeReleaseFloors`). `NativeReleaseFloor.refuses` is the one rule: active state below the floor revision, or at it when the evidence was inactive. `reconcileNativeMailboxLocked` enforces it for every allocation, `reconcileNativeSubject` checks early (administrator provisioning; quiet no-op logged once per subject) and `applyDirectory` refuses those events; inactive state always passes. Do not merge the two floor maps: `nativeRecoveryInputs` refuses published accounts at or below a recovery floor.
- Hold release (`POST /api/admin/native-recovery/release`, off unless `KYPOST_NATIVE_RESTORE_RELEASE=true`): `handleNativeRecoveryRelease` checks the flag, P6 (unlinked local administrator, password session) before and after step-up, `maddyProfile` (fails closed) and fresh `VerifyDomain` proofs outside the fences, then holds domain → settings → directory → `users.DeactivateForRestoreRelease` → session. `PlanNativeRestoreReleaseHeld` recomputes P1/P2/P3/P7/P9 with the status functions and computes every write first, including account changes (a): deactivate evidence-inactive, demote evidence-non-admin; never activate or promote. Writes, each a crash point: started audit naming accounts, `restoreRelease` intent, accounts, ledger (`commitNative`; `ErrNativeRoutesPending` is not a failure), one lifecycle write (rows, floors, `RevokedBefore` now + 31), epoch recheck and rename to `native-restore-released.json` plus `SyncDir`. Failures after the rename return `ErrNativeReleaseUnconfirmed` (released; retry confirms). An intent of the current epoch refuses until `BeginNativeRecoveryHeld` clears it; `NativeRestoreReleased` answers retries; completion audits under the record's actor and time. `applyDirectory` treats an inactive event at a release-written inactive row's revision as already applied. Log only declared keys (`reason`, `result`).

- Internal held-repair components reverify the exact stored receipt against current epoch/key/complete authority and validate existing native storage before planning activity/role changes. `users.RepairNativeAccounts` validates one bounded native-only batch and its proposed shared authority epochs before invoking the required durable intent callback, then atomically writes accounts; callbacks cannot mutate snapshots, reenter users or use the network. Repair intents bind the exact receipt and explicit before/after digests; native-only provenance barriers persist before accounts and survive later restore epochs as ordering metadata. Completion rechecks the exact resulting state, original signature, current key/epoch/expiry and storage; it requires caller-completed credential cleanup. New challenges or newer issuer events invalidate the repair journal but preserve floors/provenance. Protected `POST /api/admin/native-recovery/repair` confirms one usable legacy administrator, retains the original live-session fence through the atomic account write, then releases account/session fences before cleanup. Cleanup revokes native sessions, native device/push registrations, pairing authority and CardDAV credentials while preserving preexisting SSO-link revocation flags. Completion requires every cleanup to succeed and rechecks the original administrator witnesses. Partial failures keep the journal incomplete and hold present; request fresh evidence after remediation. The 30-second context bounds cooperative stages, not blocking cleanup locks/storage calls. Repair never releases the hold.

- `POST /api/admin/mail-relay/test` requires admin CSRF/credential/action-bound confirmation and the saved expectedGeneration. - Domain relay settings use admin credential/CSRF/action-bound confirmation and fresh DNS before the domain fence: every newly added relay domain must prove, retained ones prove when they can and at least one must (the saved-relay check uses the same rule); every relay domain must be configured and not retired under the fence; recheck authority, the saved relay and restore hold before publication. The relay holds a sorted domain set (`DomainRelay.Domains`, `RetiredDomains`; `Sends`/`Historical` are the only membership checks): a body with only `domains` uses `SetDomainRelayDomains` and keeps the generation; removing a domain is refused while `sso.NativeQueuedFromDomains` reports a queued/retryable job from it, and moves it to `RetiredDomains`. Encrypt config with the dedicated canonical secret key, redact both credentials and rotate generation on every write. Internal transport requires verified implicit TLS and AUTH, preserves uncertainty types and renders safe errors; callers must never log unwrapped provider errors. Primary-address sending uses the durable admission/claim boundary; saving credentials is not provider readiness. Pickup/system routes remain pending. See [relay contract](../docs/DOMAIN_RELAY.md).

- `receiving config <IP:port> <hostname> <cert> <key>` emits a fixed Maddy 0.9.5 qualification profile only after existing storage, TLS file and fresh domain/issuer/restore checks; every configured domain is a `destination` and at least one must currently prove. Paths reject config expansion/control syntax; TLS is mandatory, with bounded messages/headers/recipients and active transaction limits. Output is historical configuration; RCPT/DATA retain fresh authority. See [controlled receiver setup](../docs/RECEIVING_SETUP.md).

- Admin mail-domain setup uses `GET|PUT /api/admin/mail-domain` and `POST /api/admin/mail-domain/verify` for the founding domain (`NativeDomainStore.Read/Configure/Verify`), and `GET|POST /api/admin/mail-domains`, `POST /api/admin/mail-domains/{domain}/verify`, `DELETE /api/admin/mail-domains/{domain}` for the set (`ReadSet`, `ConfigureDomain`, `VerifyDomain`, `RetireDomain`). Mutations require CSRF and `confirmActor` behind `withActionDigest`; each domain's proof is immutable domain/issuer (one issuer per set) with a rotating `_kypost-mail` TXT challenge, 24-hour initial setup expiry, absolute DNS lookup/exact resolver match and at most five-minute evidence. After initial verification keep the same TXT record; every allocation still performs fresh DNS lookup. Reverify for every internal allocation; never substitute WKD proof or infer reception/SMTP readiness. Persist the domain set `$CONFIG_DIR/native-domains.json` (with `founding`); its `.lock` is the domain fence in every lock order. `VerifyDomain` refuses under its lock only when the challenge (domain, issuer, token, expiry) changed since its lookup; a concurrent refresh of the same challenge is not a change. Fences compare only touched domains through `NativeDomainSet.CurrentProof`: allocation the requested primary's domain, receiving each recipient domain (outside the set is `ingress.ErrRoute`), sending the `From` domain; never compare the whole set. Retirement refuses a restore hold, then holds domain → directory → mailbox/ingress SQLite and refuses (`ErrNativeDomainInUse`) while the relay sends for the domain, an `active` ledger address, a queued/retryable job or a pending (accepted) ingress binding uses it; staged transactions never expire and are refused at DATA after retirement, so they never block it; it keeps address records. `ConfigureDomain` re-adds a retired domain afresh (new token, not established, out of `retired`; founding unchanged unless none is in service) and its kept addresses resume once it verifies; the desired-state rule re-enables them with a generation bump. Admission refuses a primary on a retired or unknown domain; allocation records `primary_domain_unavailable` without DNS for a primary off the configured domains; the repair worker disables through `DisableNativeMailboxContext`, which refuses a subject active again. Outbound proves the `From` domain and returns `ErrNativeOutboundStale` (quarantine) for an unconfigured/retired From domain or a relay not sending for it, and checks ownership/directory staleness before requiring the proof (`withJobAuthority` returns the proof error instead of committing), so a lapsed proof only delays. System DNS is not DNSSEC or immediate revocation.

- Native addresses and aliases ([contract](../docs/NATIVE_PROVISIONING.md#addresses-aliases-and-generations)): ledger addresses are `active`, `disabled` or `reserved`, never deleted, globally unique; primaries come from KyIdentity and cannot be released/reassigned, and a KyIdentity primary equal to any existing alias/reserved address fails as `address_conflict`. Generations change only on reassign, disable, re-enable and release (+1 each; reassign appends `history`). `commitNative` applies the level-triggered desired-state rule (`active` iff owner active, no `kypost.admin` role unless `legacyMixedUse`, domain configured; `reserved` stays) on every applied directory revision inside `ApplyDirectory` (before the record), every reconcile save and the API worker's minute pass (`ReconcileNativeAddresses`, writing only on divergence), then `ingress.DeactivateRoutes` writes every non-active route inactive at its generation (no store is a no-op); failures fail the event. Ledger first, routes second: a route failure after the ledger write is `ErrNativeRoutesPending` (change durable; admin routes answer 200 + `warning`, audit `committed_routes_pending`; later commits and the worker pass retry). Aliases never take any subject's KyIdentity directory primary (`ErrNativeAddressDirectory`, 409). `saveNative` is the format-only write for migration. Admin `GET|POST /api/admin/mail-addresses`, `DELETE /api/admin/mail-addresses/{address}`, `POST /api/admin/mail-addresses/{address}/reassign` (`withAdmin` + `withActionDigest` + `confirmActor` via `nativeDomainGate`; audit names the mailbox, never the address) call `AddNativeAlias`/`ReleaseNativeAlias`/`ReassignNativeAddress` under domain → directory locks, refusing a restore hold; aliases only for everyday (non-administrator, non-`legacyMixedUse`) owners. Receiving routes carry the address generation; bind/import resolve the address through the ledger and quarantine unless it is `active`, owned by the bound mailbox and at the bound generation. Sending: the API admits `from` only as an owned active address (`nativeFrom`, else 403); `OutboundJob.FromGeneration` is set at queue and rechecked with ownership/state on every claim (`ErrNativeOutboundStale`), legacy jobs (0) pass only from the primary. Restore validates routes and bindings against the address `history` intervals (version-1 ledgers keep the primary check).

- Extra native mailboxes ([contract](../docs/NATIVE_PROVISIONING.md#extra-mailboxes)): ledger `mailboxes` of kind `extra` (ID `mbx-<uuid>`, never a user ID; owner = an account's subject; `state` is the administrator's `active`/`disabled`; `source` once prepared) with one `primary` address record; storage `$STATE/mailboxes/<id>/` via `mailbox.PrepareMailboxContext`, its `state.db` mail-only. `NativeAssignment.Dir`/`UserID` locate any mailbox; primaries stay `users/<userID>`. `CreateNativeMailbox` (reserve, prepare, record source; same address and owner resumes) and `SetNativeMailboxState` run under domain → directory locks, refuse a restore hold and drive generations through the desired-state rule (extra addresses active only while prepared and not disabled). `AdmitNativeMailbox`, `WithNativeMailAccess`, `NativeOutbound` (Queue/Send/Submit/Status/Pending/FileSent/Quarantine/Recover) and receiving import take mailbox IDs (a primary's is its user ID); unknown, foreign and disabled mailboxes refuse alike with `ErrNativeMailboxUnknown`; device fences always read the owner's primary `state.db` under `u.NativeMailboxSource`. API: `withMailbox` (inside `withMailAuth`/`withAuth`, only on mail routes, `/api/rules/run`, `/api/decisions` and `/api/export/folders`; `admitMailbox` is the same admission for a body-named mailbox, used by `POST /api/export`, `POST /api/import` and `POST /api/import/imap`; administrator subjects get the usual 403) resolves `X-KyPost-Mailbox` through the ledger on every request and sets `AuthContext.Mailbox`, answering `404 {"error":"mailbox not found"}` before any storage or cache is touched; per-user routes never see it. Mail caches (`userStores` for mailbox state, `userMailCache`, `userMail`, poller clients/stores/caches) are keyed by mailbox ID. The poller ticks each active extra beside its owner's primary (user settings/rules/labels; `uc.store` mailbox state, `uc.primaryStore()` for devices/subscriptions/notifications); sorter predictions/learning are primary-only. Incoming encryption (one journal per user, primary only) and active extra mailboxes are mutually exclusive: admin create and enable refuse an owner with `EncryptIncoming` or `IncomingEncryptionPending` (409), `PUT /api/pgp/incoming` enabling refuses a user owning an `active`, prepared extra mailbox (409; disabled or unfinished ones do not block); both sides decide under the owner's settings file lock (`fsutil.WithFileLock(userSettingsPath)`, the lock `config.UpdateUserSettings` takes), re-checking inside it, with lock order settings → domains → directory (nothing under the domain or directory lock may touch user settings), and `tickMailbox` refuses to poll an extra mailbox past that rule; never share the journal. `NativeMailbox.Prepared` (source recorded) gates the poller, outbox discovery (`outboxMailboxes`) and `GET /api/mailboxes`. A disabled mailbox's queued jobs are quarantined (`ErrNativeMailboxUnknown` wraps `ErrNativeProvisioning`). Native push data, web push and pull notifications carry `mailbox`. Backup validates extras (published native owner, root/limits, manifest, mail-only state, per-root placement), restore rotates their references, and the recovery digest includes extra mailbox records (omitted when none).

- Native storage uses the addressing v2 formats ([spec](../docs/NATIVE_ADDRESSING_V2.md)): domain set `native-domains.json`, ledger `native-provisioning.json` version 2 and relay version 2. Callers use the domain-set `NativeDomainStore` API (single-domain `Read`/`Configure`/`Verify` remain for the founding-domain routes) and the single-mailbox `NativeAssignment` API; the ledger converts on load/save, keeps `history`, carries `legacyMixedUse` on `NativeAssignment` (whose `Address` is the primary), and holds aliases beside primaries. A ledger without the `addressGenerations` marker (written before aliases) has each generation raised to the owner's directory revision on load; the first write sets the marker and freezes it. `NativeDomainStore.Read` and the ledger loader refuse (`ErrNativeMigration`, mapped to its own 503 remediation by the domain/relay handlers) a non-tombstone `native-domain.json`, a ledger that is not version 2, or a tombstone without the set or ledger; fresh installs read as unconfigured. Runtime readers accept only ledger/relay version 2; backups and `migrate-native` also read version 1. `kypost-server migrate-native` (entrypoint, runtime user) preserves `*.v1-migrated` copies, validates them (refusing a v1 ledger behind an unset initialization fence) before any write, and derives every output from them, tombstone last; keep it idempotent and crash-convergent, and never let it touch the restore hold. The recovery digest hashes the single-mailbox view, now including `legacyMixedUse`, plus every address record; add further fields to it when they gain authority. See [migration](../docs/NATIVE_PROVISIONING.md#storage-format-migration).
- Mailbox limits ([contract](../docs/NATIVE_PROVISIONING.md#mailbox-quotas)): `mailbox.NativeLimits(config.MailboxQuotaBytes())` (25 MiB message, `KYPOST_MAILBOX_QUOTA_BYTES` default 5 GiB, 1,000,000 records) for every mailbox. - **An ID token is only ever accepted through `sso.Provider.Exchange` or `sso.Provider.VerifyIDToken`, both of which delegate verification to `github.com/coreos/go-oidc`.** `VerifyIDToken` exists for exactly one caller, `verifyNativeSignOnToken`, which receives a token KyAuth obtained from KyIdentity's device grant with no browser round trip; it skips the nonce and at_hash checks that only a code flow can make and replaces them with `signon_method == device`, an `iat` no older than five minutes and a single-use `jti`. Nothing in this repository parses a JWT by hand. Shared verified ID-token decoding requires positive `iat` at most 30 seconds ahead of the server before either browser or device claims can grant authority; native device sign-on retains its five-minute age bound. Issuance alone is not fresh primary-authentication or restore-release proof. The removed `ParseClaims` base64-decoded the payload and trusted it — no signature, issuer, audience, expiry or nonce — so anything that could answer the token endpoint minted `{"role":"admin"}` and got an administrator session, and the tests enshrined it by using `"header." + base64(claims) + ".sig"` as a valid token. Verification requires: a signature from the issuer's JWKS using one of `allowedSigningAlgs` (asymmetric only — HS* is excluded because it signs with the client secret, and `none` is refused by go-oidc), `iss` equal to the discovered issuer, `aud` containing the client ID, unexpired `exp`, `nbf` not in the future, `at_hash` matching the access token when published, a non-empty `sub`, and, for `Exchange`, a `nonce` equal to the one this browser's login stored (`VerifyIDToken` skips nonce, at_hash and the userinfo top-up). `sso/ssotest` exists so every one of those can be violated on purpose in a test and watched get refused
- **A back-channel logout token is verified only by `sso.Provider.VerifyLogout`, which is `ky-primitives/oidcverify.VerifyLogout`, never by the ID-token verifier.** go-oidc has no notion of token purpose, so it would accept a logout token as a login and a login as a logout; `oidcverify` demands `typ: logout+jwt`, the backchannel-logout `events` member, a `jti`, no `nonce`, RS256 from the issuer's JWKS, and an `https` issuer — a LAN issuer allowed by `AllowInsecureIssuer` therefore has no back-channel logout, and `VerifyLogout` says so. Login stays on go-oidc deliberately: it verifies ES/PS signatures for Authentik and Keycloak, which `oidcverify` (RS256 only) cannot. **Admission is durable and happens before revocation**: `sso.LifecycleStore.RecordLogout` writes the `(issuer, client, jti)` under `fsutil.WithFileLock` and refuses a second delivery, retained through `max(token replay window, now + ssoLoginLifetime)`, so a replay after a restart revokes nothing and a callback still in flight when the logout landed is refused by `LoggedOut` at sign-in. Scope is `sso.LogoutEvent.Covers` and nothing wider: a `sid` ends exactly that session (checking `sub` when the token carries one), a subject-only token ends that subject's sessions issued no later than the token's `iat`, and an unknown `sid` is a successful no-op — never a subject-wide logout. Password sessions carry no `SSO` identity and are never covered. The per-IP limiter is charged before discovery (an outbound fetch to the provider) and refunded once a delivery is accepted, so junk pays for itself and a burst of real logouts is never throttled. `sso.SetTransport` panics outside a test binary
- **An SSO session's privilege is bounded by the token's verified role ceiling AND the local role; the token never raises the local role.** `sso.SSOTokenClaims.AppAdmin` is the one mapping: a token carrying `roles` is the KySignOn contract and is admin iff the array names `sso.AdminAppRole` (`kypost.admin`), with every other claim ignored; a token without `roles` is a generic provider and the Authentik/Keycloak admin group names are mapped. KySignOn's legacy `role` claim is the central global admin and has no field on the claims type at all, so it cannot be mapped by accident. The result is stored on the session as `Session.SSOAppAdmin`; `currentUser` caps an SSO session without it to `users.RoleUser` even when `users.json` says admin, so `/api/auth/me` and every admin route see the capped role. Login provisions a new account with the token's role and never changes an existing account's role: the directory (`POST /api/sync/webhook`) is the only writer of roles for a KySignOn subject, and it ends sessions when it changes one
- **An SSO session re-proves presence to KySignOn, bound to one exact request, never with a password it does not have.** `confirmActor` is the one step-up gate: a session with `Session.SSOKySignOn` set (its token carried the `roles` contract, `sso.SSOTokenClaims.KySignOn`) goes through `confirmSSOStepUp`; every other session, password or generic-provider SSO, goes through `confirmAccountCredential` as before. A wrong credential or second factor (`confirmAccountCredentialNoRecord`, `confirmSecondFactor`) answers 403 with `invalid credentials`/`invalid code`, never 401: the session is valid, and the web client treats 401 outside `/api/auth/` as an expired session and reloads; the 403 still spends a step-up throttle strike. That routing is deliberate: `FreshProof` speaks only KySignOn's `acr`/`amr` vocabulary, so an Authentik or Keycloak session sent to its provider would be refused forever, whereas the credential check fails closed by itself for an account with no credential and lets one with a password through. That mints a challenge bound to the action digest `withActionDigest` computed (sha256 of method, request URI, content type and body — so the route must be wrapped in it, and a route that is not is refused with 500 rather than gated on nothing) and answers 403 with the challenge id. `handleSSOStepUpStart` claims the challenge once for the minting session and sends the browser to the provider with `prompt=login&max_age=0&acr_values=urn:kysignon:acr:password`; `completeSSOStepUp` in the callback accepts the token only for the session's own issuer and subject and only when `sso.SSOTokenClaims.FreshProof` holds (auth_time inside the challenge window and not after issuance, `pwd` among the methods, password or MFA-with-a-factor assurance, never `urn:kysignon:amr:recovery`), marks the challenge verified for one more minute, and mints no session; a failed proof discards the challenge so the action restarts. The replayed request carries the id in `X-Kypost-Step-Up` and the grant is consumed exactly once, for the identical digest, by the same session. Challenges are in memory like sessions, one live per session, and another session can neither see, start nor cancel them. Gated today: `POST /api/auth/step-up`, every mutating `/api/admin/backup/*` route, mail-domain and mail-address mutations. **PGP identity operations deliberately keep the password**, because there it is also the vault credential the browser derives keys from, and the SSO link start keeps the local credential because linking is what gives a local account a second way in
- **A local account is claimed by SSO only through a stored `sub`, or through a session already authenticated as that account.** Never by username or email. Matching `preferred_username` against `users.GetByUsername` treated a name collision as authentication: any directory user who set `preferred_username=admin` was silently linked to the local administrator and signed in with its role — and a correct signature does not fix it, because the IdP genuinely signed the name the attacker chose. The link flow's target likewise comes from `s.currentUser(r)` at callback time, never from the state cookie; the cookie is attacker-supplied, so storing a user id in it let anyone who knew a victim's id bind their own identity to that account. **And the target being right is not the same as the write being authorized**: the link creates a credential, so it takes the step-up every other durable self-service mutation takes. `POST /api/settings/sso/link` checks the credential and the second factor, then records `SSOLinkGrantedAt` **and `SSOLinkState`** on the caller's own session; `handleSSOCallback` spends that grant through `consumeSSOLinkGrant` before `linkSSOIdentity` writes, so one step-up authorizes exactly one link. **The state is what makes it exactly one**: a timestamp alone authorizes any link-mode callback in the window, and the state cookie is unsigned and caller-written, so whoever holds the session can start their own plain sign-in, relabel its cookie link-mode — the `ssoSessionTag` included, since they hold the session it derives from — and spend a grant the real user minted seconds earlier, binding their own subject. The state token is minted into the victim's cookie and shown to nobody else, so requiring it back ties the grant to the flow that paid for it. A failed check clears the grant rather than leaving it live, and is metered on `loginParamsLimiter` so it is not a free oracle for when one exists. The grant is recorded only AFTER `startSSOFlow` succeeds, so a discovery or token-generator failure mints nothing. The grant is deliberately SERVER-SIDE rather than a signed ticket in the state cookie: whoever holds the session controls their own cookie jar, so anything stored there has to be unforgeable to be worth anything, while a fact on the session cannot be written by the caller at all. `ssoSessionTag` still binds the cookie to one session, but it is not the authorization — an attacker holding the session can reproduce the tag. `linkSSOIdentity` also refuses a `sub` already linked elsewhere, so one subject can never resolve to two accounts
- **The OIDC `redirect_uri` comes from `s.serverBaseURL` and from nothing else.** `api.ssoRedirectURI` is the only place it is built, it takes no request, and it returns `""` when `SERVER_BASE_URL` is unset — `ssoProvider` then refuses the login with "cannot determine this server's external URL; set SERVER_BASE_URL". Behind a reverse proxy `r.Host` is the internal name, so a Host-derived value matches nothing registered at the provider and every SSO login fails anyway. The real reason is the other one: OAuth pins `redirect_uri` across both the authorize and token calls, so a request header must not get to choose where an authorization code is delivered, and the provider's own allowlist is the only thing that would have caught it
- **The OIDC issuer is admin-configured, so it is held to a transport policy rather than to `netguard`.** `sso.requireSafeURL` demands https, allowing cleartext http only for loopback or when an operator sets `AllowInsecureIssuer`; it is applied to the issuer at save time and again to every endpoint discovery names, so a discovery document cannot downgrade the token endpoint and collect the client secret. Redirects are refused outright and every response body is capped at `maxOIDCResponseBytes`. Deliberately **not** screened through `netguard.IsPrivateOrReserved` like CardDAV and UnifiedPush: those are user-supplied URLs where reaching the LAN is the attack, whereas an identity provider on the operator's own LAN or tailnet is the normal deployment for a self-hosted server
- **OIDC discovery is cached, and the public SSO routes are metered per IP.** `oidc.NewProvider` fetches `<issuer>/.well-known/openid-configuration` on every call, and `sso.NewProvider` was called once per request by four PUBLIC routes — so an unauthenticated GET to `/api/auth/oidc/login` was a 1:1 reflector at the operator's identity provider and a socket held here for up to the 15 s client timeout, with no global rate limiter in front of it. The cache is package-level in `internal/sso`, keyed on a hash of every setting the provider is built from (issuer, client id, client secret, redirect URI, `AllowInsecureIssuer`), so a settings change IS the invalidation and the TTL only covers a provider rotating its own endpoints; failures are never cached, because pinning an outage would make a restarted IdP look broken for minutes. The rate limit is the other half and is not optional: a cold cache, a settings change or a provider that is down all put the fetch back on the request path. Both `handleSSOLogin` and `handleSSOCallback` spend `s.loginParamsLimiter` on `lockoutKeyForIP(clientIP(r))` — the callback because the state cookie is unsigned, so anyone can mint a self-consistent state/cookie pair and reach the token exchange, which is an outbound POST carrying the client secret. The callback spends its token only after the cheap local checks pass, so malformed floods cost a caller nothing and cannot deny a NAT its own sign-ins
- **`POST /api/sync/webhook` applies the directory's versioned desired state, never a bare command.** KySignOn delivers a SCIM User signed with `ky-primitives/syncauth` (HMAC over timestamp, event type, event ID and body hash; verified against the in-memory pairing secret first and only then the SSO client secret, so an unsigned flood never reads `sso.json`; keys shorter than `syncauth.MinKeyBytes` skipped); `meta.version` is a monotonic `W/"n"` revision. `sso.LifecycleStore.ApplyDirectory` runs under the file lock in this order: refuse revisions at or below any recovery barrier, refuse a reused event ID with a different body, refuse a revision older than the applied one or the same revision with a different body (422, because the sender counts 409 on `user.created` as success), run the apply, then record the state and the event. A crash after apply and before the record makes the retry apply again, and every apply is idempotent, so nothing is ever told "already applied" that was not. A disabled or deleted user is `Deactivate` + `revokeAllUserCredentials`: sessions, devices, CardDAV password, the SSO link flag on an account with a local credential, the subscriber id. **Never the mailbox, keys or account record**, so a `user.updated{active:true}` rehires the same account. The last active admin can be neither removed nor demoted (422, the fence stays at the prior revision, so the same event applies once the directory has promoted somebody else). An account with a local credential also gets its SSO link flag revoked on deactivation, exactly as after an admin password reset; a rehire restores the account and the user re-authorizes the link from a local sign-in. `sso.DirectoryState.RevokedBefore` advances on every deactivation and role change; `handleSSOCallback` and native sign-on refuse a token issued before it, and a subject the directory disabled outright, before `linkSSOIdentity` can link it or `resolveSSOUser` can auto-provision it; both read the fence and provision under `LifecycleStore.LockDirectory`, so a disable for an unknown subject, which writes only the fence, cannot land between the two. Role comes only from `sso.HasAdminRole` over the SCIM `roles` (`kypost.admin`); an unrelated role name grants nothing and blocks nothing. The old `{jti,iat,event,user}` envelope, `X-Sync-Signature`, the bearer-secret form and `RequireFreshEvents` are gone: replay protection is not optional

- **Every writer of a user's PGP identity must ALSO clear device enrollment, in the other store.** The rule below covers `PGPWrappedEnvelopes` in `users.Store`; the enrollment record (`enrollment_public_key`, `enrollment_key_at`, `encryption_enrolled`, `enrolled_version`, `enrolled_generation`, `enrolled_fingerprint`) lives in `state.Store`, which `users.Store` has no coupling to, so the two halves cannot be done in one place. Skipping it leaves a device reporting itself enrolled with a stale published key, naming an envelope that no longer exists — and it fails worst in the flow it breaks, because rotating the identity is the documented way to un-enroll a *lost* phone (the server cannot reach the copy that phone re-sealed into its own keystore), so the Security page went on showing that phone as protected immediately after the user acted to revoke it. Pinned by one test per call site in `pgp_identity_enrollment_reset_test.go`, deliberately not table-driven: the failure being guarded against is a fourth writer arriving and only some call sites being updated.

- **PGP revision advances at the shared users-store mutation sink** when identity material, the recovery slot or password-derived credential fields change. Converted-account enforcement belongs to the later lifecycle transaction. Never reset the counter when deleting an identity. - **A proof authorizes exactly what it proves — the address, and the challenge.** Two places derive trust from inbound mail and both had drifted from that:
  - Send-as verification (`processor/sendas_check.go`) requires a DKIM signature from the alias domain covering Subject and From, with the signed From equal to the alias — **and the signed Subject must contain that alias's `VerificationCode`**, and the message must not predate the challenge. Without the content check the code was only the IMAP `SEARCH` term, so the trust anchor was the answer of a server the ACCOUNT HOLDER chose (`POST /api/imap/config` stores any host, unverified) and one genuine archived message from the target satisfied the alias. An `Auto-Submitted` reply is refused for the other half, so an out-of-office at the target address cannot satisfy the remaining checks by itself. The probe is sent as the alias, to the alias, through the user's own SMTP (`api/sendas_handlers.go`): an upstream that refuses that From refuses the alias. The DKIM loop-back is one of two ways to verify; the other is `POST /api/mail/send-as/{id}/confirm`, where the user types the mailed code (`sendas.Store.Confirm`: constant-time compare, five wrong codes fail the record, 30-minute window). **The two proofs authorize different things** (`sendas.Alias.DomainProven`): the code went through an SMTP server the user chose, so it proves nothing about the mailbox and unlocks the From header only, which that SMTP server may refuse; WKD publication (`publishableAddressesAt`) and key User IDs (`suggestedKeyUserIDs`) require `VerifiedBy == dkim`. The daemon keeps checking a code-confirmed record until it expires so the DKIM match can upgrade it. The list handler blanks `VerificationCode` before responding; serving it would let any session verify any address.
  - Autocrypt harvest (`processor/autocrypt_harvest.go`) authenticates the header against the FROM address's own domain, so it may only bind that one address. The key is stored on the contact RECORD and `findContact`/`contactBindsAddress` match ANY address on it, so a key proven for a lapsed secondary domain became the encryption target for the primary one — a confidentiality break, and the newest-fingerprint-wins branch *replaced* a legitimate key rather than filling a gap. Until the model has a per-address key slot, `authenticatedForContact` refuses the cases a record-wide write would overreach.
- **Contact key material is validated wherever it enters, and pinning is not validation.** `validateDiscoveredKey` (WKD) and `validateAutocryptKey` both require a key to parse, be usable, and carry the address as a User ID; `contactFromVCard` — which backs CardDAV pull, CardDAV PUT and vCard import — stored whatever arrived. `pinPGPKeyFingerprint` derives the pin FROM the supplied key, so `keyMatchesPin` then passes on anything, and an unparseable key yields an empty pin which is accepted by design. A contact's key decides what mail is encrypted to and what the signature badge is computed against, so a fourth ingest path restates the check or calls `validateContactVCardKey`
- **A CHANGED key is not a MISSING key, and the pickup fallback covers only the latter.** `resolvedKey.Tier` must be carried into `pgpRecipientPlan`, not collapsed to `(Armored, Usable)`: `tierKeyChanged` also carries `Usable:false`, so collapsing it folded a broken TOFU pin into `withoutKeyEmails`, where `AllowPickupFallback` stores the message plaintext server-side for seven days and mails an unauthenticated link in the clear — to whoever is in a position to have substituted the key. Key-changed recipients are refused outright and the fallback cannot override them. The browser path always refused this; the two must not disagree
- **The pull queue is addressed, not broadcast.** `SendNativePushToDevices` writes every notification to `pull_notifications` in both delivery modes with the target `DeviceIDs`, and `PullNotificationsAfterStrict(deviceID, after)` returns a device only entries addressed to it or to everyone. Push-MFA dispatches to approver-eligible devices only, and the queue must not widen that set: an excluded device reading challenge IDs and match digits from the queue defeats the eligibility filter. `DeviceIDs` is `json:"-"`; the client never sees the recipient list.
- **A message's audit decision and its processed marker are one state change and must be written by `state.Store.RecordProcessedDecision`**, never as two statements. Every terminal path in `poller.handleMessage` ends in both writes, and they used to be issued separately — in opposite orders on different branches, with the errors dropped on some. Both orders lose: decision-then-marker reprocesses the message on the next tick (duplicate decisions, a second notification to every paired device), marker-then-decision retires it with no record that anything happened to it. SQLITE_BUSY past the busy_timeout is reachable because the api and daemon contend on this file, so neither is hypothetical. A non-terminal decision (a rule matched but did not `stop`) still uses `AddDecision` alone, because the message goes on to classification, which retires it
- **Push registrations are capped per account** (`state.MaxNotificationSubscriptions`, `state.MaxNativeDevices`), the cap is checked inside the same transaction that inserts, and `POST /api/notifications/test` is metered per user. Not a storage concern: both fanouts are serial, each destination gets its own multi-second network timeout, and they run inside the goroutine `poller.tick`'s `wg.Wait()` awaits — so the row count is a multiplier on how long the *whole instance's* polling is held up. Refreshing a registration that already exists never hits the cap (a browser at the cap must still be able to rotate its keys); a genuinely new one past it gets 409. `processor.pushFanoutBudget` bounds one fanout across every destination, which is the half the cap cannot cover. **A request the server refuses must not spend the caller's meter**: `POST /api/notifications/test` decodes and validates before `tryConsume`, and rejects a malformed body 400 — consuming first (over a decode whose error was discarded) sent the default notification anyway and left the caller unable to retry the request they meant
- State collection readers with security or user-visible consequences have `*Strict` variants returning errors (`ListNativeDevicesStrict`, `ListNotificationSubscriptionsStrict`, `DecisionsStrict`, `PullNotificationsAfterStrict`); callers must not turn a database failure into an empty result
- **Every place that validates a TOTP code must record `SetLastUsedTOTPStep` after it passes, and nowhere else.** The replay guard is scoped to the ACCOUNT, not to the endpoint or the challenge, and there are now three checkers: the login challenge (`server_auth_session.go`), enrollment confirm (`mfa_handlers.go`) and session step-up (`auth_stepup.go`). One that validates without recording leaves a captured code replayable against the other two inside its 30-90s window; one that records before every other check has passed lets a rejected request burn a step. The consequence users see is that a code is spent everywhere at once — signing in and then opening the Security page needs two codes, which is the guard working, not a bug to route around
- Push-MFA device eligibility is a security decision: enrollment and login challenge creation must use `mfaApproverDevices`, propagate its strict-read failure as 503, and never create a push-MFA challenge from an unreadable device set
- **A push challenge is redeemed on `mfa.Challenge.FinishSecret`, never on the challenge id.** The id is in the notification payload, so the relay operator, Google and Apple all read it the moment a challenge is dispatched — and `POST /api/auth/mfa/push/finish` is a public route that mints a full session. On the id alone, any of them could poll `/api/auth/mfa/push/poll` until the genuine user tapped Approve and then call `/finish` first, riding a real approval so number matching never applies (it is verified against the *device's* answer, and the attacker never answers it). `Store.Create` mints the secret, the login response is the only place it appears, and `dispatchPushChallenge` is not passed it at all — that missing parameter is what keeps it out of the payload, so keep it that way. A wrong secret reports `ErrChallengeNotFound` and leaves the challenge intact, so a probe cannot burn the approval the real browser is about to redeem. `POST /api/mfa/push/respond` is unchanged: the phone still answers with the id from the payload plus its own device credentials, so no mobile client change is involved
- **Every `http.ResponseWriter` wrapper in `api/` must implement `Unwrap() http.ResponseWriter`.** `withGzip` is the outermost middleware, so its `gzipWriter` is what every inner handler receives for any client that offers gzip — that is, every browser. `http.ResponseController` reaches the connection by looking for the method it wants or for `Unwrap`, and finds neither on a bare `struct{ http.ResponseWriter }`; it then returns `ErrNotSupported`, which callers routinely discard. That is how `withUploadDeadline` silently became a no-op on every upload route, leaving the 60s server-wide `ReadTimeout` in charge. The failure is invisible — no error, no log, the middleware still runs
- An account can authenticate four ways — web session, paired device secret, CardDAV Basic Auth, **and a linked SSO identity** — and all four are revoked together by `revokeAllUserCredentials`. Any admin action that cuts off access (deactivate, reset-password, clear-MFA) must call it rather than revoking sessions and devices individually. The SSO link is a credential because `handleSSOCallback` signs a caller in from the stored `sub` plus an `Active` check and nothing else, and it is a credential a SESSION CAN CREATE: linking used to ask for nothing but the caller's own session, so a hijacked session could bind an outside directory identity to the account and every revocation path left it in place — the victim's own password change included. Linking now takes a step-up (above), and revocation now cuts the link: `revokeAllUserCredentialsExcept` calls `users.RevokeSSOLink`, which does its own read-modify-write inside the store's file lock, so it cannot clobber the password the same request just wrote. A reactivated account must re-link, exactly as it must re-pair its devices and re-create its CardDAV password — `LinkSSO` clears the revocation, because the step-up is the proof it was waiting for. **The link is revoked by FLAG (`SSOLinkRevokedAt`), never by erasing `SSOSub`, and it is the one credential that is sometimes not revoked at all.** Both follow from the subject doing two jobs at once: it is the proof `handleSSOCallback` signs a caller in on, AND it is the address every `sync_handlers.go` event is resolved through. Erasing it to revoke the first destroys the second — a later `user.updated{active:true}` for that subject finds nothing, `applySyncEvent` answers 200 for a subject it does not know, and the directory stops retrying an account it can now never reactivate. So `GetBySSOSub` keeps resolving and `resolveSSOUser` refuses a revoked link instead (a 403, never a fall-through to auto-provision, which would hand the same subject a second empty account). The exception is an account with no `PasswordHash` — an auto-provisioned one, where the link is not a fourth credential but the only one. Revoking it would leave nothing that can authenticate and no way back, since a re-link needs a step-up and a step-up needs the credential that account has never had; `User.HasLocalCredential` gates it, and what covers those accounts is the `Active` check the callback still makes. The CardDAV credential cache additionally re-checks `u.Active` on every hit, so a deactivated account is refused even if it populated the cache in the window between the deactivation and the invalidation; the cache saves the scrypt verification, never the authorization decision. Clearing the cache is only half of revocation, because a verification already in flight lands its `put` after the clear — so the cache carries a generation counter that `invalidateUser` bumps and `put` compares against a snapshot the caller took **before** it read the credential. That covers what the `u.Active` re-check cannot: a password reset leaves the account active, so only the generation stops a deleted app password from being re-admitted for a full `davCredentialTTL`
- **A client-declared login parameter is bounded at BOTH ends, and the bounds are a contract with the browser.** `users.MinLoginIterations`/`MaxLoginIterations` and `validateLoginSalt` gate every write (`SetDerivedAuthAndRewrapPGP`, `UpgradeToDerivedAuth`); `MaxLoginIterations` must equal `MAX_ITERATIONS` in `frontend/src/lib/authSecret.ts`, pinned by `TestLoginIterationCeilingMatchesFrontend`. The floor stops a downgraded client registering a credential derived at no cost. The ceiling exists for the opposite reason: the work factor is a cost the *browser* pays on every sign-in forever, so a value the client refuses to derive with bricks the account — and the only interface for fixing it is the client that can no longer sign in. Out-of-range values are **rejected, never clamped**: the stored count must be the one the client actually derived with, so substituting a different number pins the account to a credential nobody can reproduce. `loginParamsFor` clamps on the READ side only, to cover anything persisted before the ceiling existed. The legacy upgrade in `handleLogin` recomputes the salt server-side and requires the echoed iteration count to equal what `loginParamsFor` issues, rather than trusting or clamping it. **It also verifies that the auth secret IS the derivation of the password it just checked** (`users.DeriveAuthSecret`, constant-time compare). Re-verifying the plaintext proves the caller knows the password and says nothing about the value being pinned as the new credential — without the derivation check, anyone holding the current password (an admin-issued temporary one, say) pinned the account to a credential of their own choosing, on a request that returns `mfaRequired` and never proves a second factor, and `SetPassword` reverts accounts to legacy so every admin reset reopened it. The upgrade is the one moment the server holds both values, which is what makes the claim checkable at all. `DeriveAuthSecret` must stay byte-identical to `frontend/src/lib/authSecret.ts` or every legacy sign-in breaks; pinned against a WebCrypto-computed vector by `TestDeriveAuthSecretMatchesTheBrowser`, not merely against itself
- **Any per-account state keyed off a client-supplied username must key it off `users.NormalizeUsername(...)`**, the same fold `GetByUsername` resolves the account with. The login lockout keyed on the raw string, which made `"victim"`, `"Victim"` and `" victim "` one account to the lookup and three independent strike budgets to the lockout — with whitespace padding that key space is unbounded, so three-strikes became unlimited online guessing from one IP. **And every caller-supplied key component passes `clampLockoutKeyComponent`.** Normalizing folds case and trims; it does not truncate, and the login body allows 64 KiB, so the caller sized the table's MEMORY as well as populating it — `loginLockoutHardCap` bounds how many entries exist, not how large each one is, which at the cap is the difference between ~6 MiB of keys and ~3.1 GiB. A map bounded by count is not bounded
- **Recovery-code digests are KEYED, and the key does not live on the config volume.** `mfa.NewRecoveryCodeDigester` reads `$SECRET_DIR/totp-secret.key` once per process and returns HMAC-SHA256 under an HKDF subkey labelled `kypost:recovery-code:v1`; `api.Server` holds it and passes it into `users.Store.ConsumeRecoveryCode`. A code is 60 bits (`recoverycode.Alphabet`, twelve symbols) and redeeming one is a full second-factor bypass, so a bare SHA-256 in `users.json` is GPU-days of offline search for anyone holding a backup of the config volume — which is a *different* volume from `SECRET_DIR` (`docker-compose.yml`), and that separation is the whole control. The store must never read the key file itself: pepper and peppered value on one volume is no pepper. A password KDF is still the wrong answer here (60 bits of `crypto/rand` is unreachable online, and `mfaLockout` caps that at ten attempts per account per 15 minutes) — the key is what prices the offline attack, at one HMAC. `scrypt$` entries from before digests existed keep verifying through the legacy loop and drain as users regenerate
- **`mfaLockout` is the second-factor code budget, and nothing else spends it.** It is keyed on the bare account id deliberately: a password holder can mint unlimited fresh sign-in challenges, so only a cross-challenge account-wide counter keeps a six-digit TOTP code out of reach of online guessing (`login_lockout.go` states this). That makes it the wrong counter for anything else — step-up spent it on a PASSWORD check, so ten wrong passwords from a stolen session denied the OWNER both TOTP and recovery codes, from a different address, renewably. Credential confirmation uses the password-shaped `(account, client IP)` throttle instead (`stepUpLockoutKey`), which is the same shape `handleChangePassword` uses for the same secret. Do not "fix" the asymmetry by composing an IP into `mfaLockout`; that reopens the brute-force window it exists to close
- **The per-account write meter is applied by EVERY auth wrapper**, through the shared `meterAccountWrite`. It was placed at the wrapper rather than at the endpoints precisely so a new route inherits the bound without anyone remembering to ask for it — and then only `withAuth` called it, leaving the ~26 `withMailAuth` routes plus every device-credential and CardDAV route unmetered. Those wrappers carry the expensive paths (rules run, recipient resolution, pickup creation), so the gap was not a missing nicety; it was what removed their rate bound. Reads stay unmetered on every wrapper
- Login CAPTCHA is an operator opt-in (`CAPTCHA_PROVIDER`) with three providers: `turnstile` and `friendly` verify a token against a third-party siteverify endpoint; `pow` is self-hosted (`captcha/pow.go`) and verifies an HMAC-signed hashcash challenge this server issued via `GET /api/auth/pow-challenge`. All three are checked in `handleLogin` before scrypt, so a bad solution never pays the password-hash cost. `pow` alone reports two outcomes as distinct errors so they refund the lockout strike instead of spending it: `captcha.ErrChallengeExpired` (a stale tab) and `captcha.ErrChallengeWrongClient` (the solution arrived from a different address than the challenge was issued to — a phone changing networks mid-solve). A wrong solution still spends one. Its three maps (spent salts, per-IP challenge budget, per-IP difficulty escalation) are swept by `StartPoWSweeper` in both `app.go` mode blocks. The first two are swept only when `pow` is the configured provider; the escalation map is swept **unconditionally**, because `handleLogin` records a failure against the client IP on every failed login whatever `CAPTCHA_PROVIDER` says — skipping the sweep on a default install left an unbounded map on the installs that never opted in.
  `pow` difficulty is adaptive: `powEscalation` (`api/pow_escalation.go`) multiplies the base `maxnumber` by 4 per recent failed login from the same client IP, capped at 1,000,000 and decaying after 15 minutes or on success. It keys on IP alone because the challenge is issued before the user has typed a username. The cap is load-bearing — uncapped, a persistent attacker drives the difficulty past what anyone behind that address can solve. A challenge is bound to the IP that requested it: `IssueAt` takes the client IP, puts it in the `clientip` field **and** in the signed preimage, and `Verify` compares it against `remoteIP`. Both, not just the preimage — carrying it in the payload is what lets `Verify` tell "your address changed" (`ErrChallengeWrongClient`, strike refunded) from "this signature is forged" (plain false, strike spent). The address check sits after the signature and expiry checks and before `consume`, so a foreign solution never burns its salt and a user retrying from the issuing address still succeeds. What escalation is still worth is bounded: it counts per address, so an attacker spraying from many addresses gets the base difficulty at each. It prices repetition — not a distributed attacker.
- **Every route in `server.go` must declare its auth model on its own line**, and the marker must be TRUE. Four tests enforce it: `TestEveryRouteDeclaresItsAuthModel` (a marker is present), `TestAuthMarkersMatchTheirHandlers` (the handler makes the call the marker claims — `withDeviceAuth`→`deviceAuthFromRequest`, `withTokenAuth`→`validatePairingToken`/`consumeQRToken`/`decodeAndVerifyPairingToken`, `withSelfAuth`→`currentUser`), and `TestAuthMarkersAreInert` (the markers stay no-ops). Use the middleware that gates it (`withAuth`/`withMailAuth`/`withAdmin`/`withDAVBasicAuth`), or the inert marker that says how the handler authenticates itself (`api/route_auth_markers.go`). Presence alone was not enough: the fastest way to green a forgotten `withAuth` was to type `withPublicRoute`, and a marker that lies launders "someone forgot" into "documented decision" — the first run of the match test found `/api/notifications/native/register` marked `withDeviceAuth` when it actually verifies a pairing token. `withPublicRoute` has no call to verify, so it is constrained two ways: the `publicRoutes` allowlist in `route_auth_test.go`, which demands a written reason per route, and `TestPublicRoutesDoNotAuthenticate`, which fails if a handler marked public calls an auth primitive at all. The allowlist alone was not enough — it accepts free prose, and `POST /api/mfa/push/respond` sat in it justified as authenticating "with the signed push nonce", a mechanism that does not exist anywhere in this codebase, while the handler's first act was `deviceAuthFromRequest`. A negative is checkable where a rationale is not. A rate limiter (`withWKDRateLimit`) is not an auth model
- **`Server`'s mutexes have a declared rank and it is machine-checked.** `lockRank` is the complete order; `backupDrainMu` is innermost and never acquires another Server mutex. `TestLockOrderIsRespected` parses this package and fails on a function that takes one while holding a higher-ranked one — directly, or through any call chain inside `api/`. Adding a mutex to `Server` means adding it to `lockRank` in `lock_order_test.go`; one missing from that map is not merely unchecked but invisible — `mutexCall` ignores it, so every acquisition of it in any order passes. `TestEveryServerMutexIsRanked` therefore parses the `Server` struct and fails when a `sync.Mutex`/`sync.RWMutex` field has no rank (and when a rank names a field that no longer exists), so the suite cannot go green because someone forgot the step. It was not hypothetical: `pinProbeMu` shipped unranked. The rule was stated in `Server`'s doc comment and enforced nowhere, alongside the note that "nothing currently takes more than one, which is the only reason there is no deadlock to find today" — an ABBA deadlock that appears only under concurrent load in production, which no unit test would provoke. A deferred `Unlock` is deliberately NOT treated as an unlock at its source position: `defer mu.Unlock()` is written right after the `Lock`, so honouring it there releases a lock held for the rest of the function and silently defeats the check, since every critical section here is written that way.
- **Rate/cooldown state is one type per ALGORITHM, not one per call site.** `cooldown` (per-key "not again for N", send-as probes and classifier tests) and `singleUseTokens` (one-shot tokens: pairing nonces, spent QR tokens) each replaced two byte-identical copies. Copies do not inherit the fix made to the original, and both pairs had drifted: only one cooldown had a sweep, and only one token store hashed what it kept — the other held raw bearer values in a map that ends up in a heap dump one day. `singleUseTokens` keys are namespaced per caller (`qr:`, `pair:`) because one map now backs two token systems. The genuinely different algorithms — `failureLockout` (strikes), `ipRateLimiter` (token bucket), `powChallengeLimiter` (fixed window), `mfaPushLimiter` (sliding window) — stay separate; merging those would be forcing unlike things together, not deduplication.
- **The KDF concurrency limit lives in `internal/users`, next to the derivation it bounds** (`users.MaxConcurrentKDF` = 4 × 64 MiB for an Argon2id derivation; a legacy scrypt verify holds 128 MiB instead). The `ky-primitives/password` library enforces a second, independent admission budget of its own (`password.MaxMemoryKiB` = 256 MiB total, `password.MaxLanes`, its own 2 s wait) that a kypost slot waits inside — see `kdf.go`'s comment on `MaxConcurrentKDF`/`KDFMaxQueueWait` for the worst-case wait this composes into. Every exported way to derive a key — `HashPassword`, `VerifyPassword`, `VerifyAuthSecret`, `VerifySecretHash`, `VerifyDeviceSecret`, and the `Store` methods that hash (`Create`, `SetPassword`, `SetDerivedAuth*`, `RehashPassword`, `UpgradeToDerivedAuth`, `ConsumeRecoveryCode`) — takes a `context.Context` and acquires a slot itself, so a caller CANNOT forget it. It used to be `Server.withKDFSlot` in `internal/api`, which every caller wrapped by hand and whose doc comment named four callers as though that were all of them; MFA confirm, `requirePasswordConfirm`, recovery-code generation, CardDAV app-password generation, the hash and PGP rewrap at the end of a password change, and admin create/reset all reached `scrypt.Key` around it. A ceiling half the callers walk around is not a ceiling. **These functions RETURN AN ERROR and it is not "wrong credential" — handle it.** After `users.KDFMaxQueueWait` (2 s) they return `users.ErrKDFBusy` without deriving; a caller that folds that into `false` reports "the server is overloaded" as "your password is wrong", which is a lie and a lockout. Every shed path must (a) answer `writeKDFBusy` (503 + `Retry-After`) and (b) REFUND the lockout strike it reserved, because no credential was examined — same reasoning as `ErrChallengeExpired`. The instance-wide login budget is a *rate* limit and admits before the work runs, so it does not substitute for the slot. `users.WithKDFSlot(ctx, fn)` holds one slot across a region and hands back a context that already holds it, so nested derivations reuse it rather than deadlocking against themselves; it exists for `chargeLoginKDF`, which must start its stopwatch AFTER the queue (the budget meters real seconds, and a 2 s wait billed against a 200 ms reservation empties the instance bucket). Do NOT wrap `ConsumeRecoveryCode` in it: for an account whose codes predate digests that check is up to `recoveryCodeCount` scrypt derivations and takes a slot PER comparison on purpose — one slot held for ~2 s is a quarter of the instance's capacity, and four such callers stall every login. A digest account costs one keyed HMAC and no slot at all, so the rule is about the legacy entries, and it stays until they are gone. Pinned by `TestEveryDerivationEntryPointSharesTheOneLimit`, which drives every entry point above under a saturated semaphore. **On the device-credential path that signal rides `retryAfter`, which therefore has three states, not two**: `0` = bad credentials (401), positive = locked out (429 with `Retry-After`), and `retryAfterKDFBusy` (negative, so it can never read as a cooldown) = the secret was never compared. A new caller of `deviceAuthFromRequest` routes it through `writeDeviceAuthFailure` rather than testing `retryAfter > 0` itself; `withMailAuth` is the one caller that renders it separately, via `mailLockedOutError.kdfBusy`, and must answer the same `writeKDFBusy`. `VerifyDeviceSecret` reaches scrypt for any untagged (pre-`HashDeviceSecret`) hash, so this is live on every install predating that format — and it failed in the worst place, telling a phone its credential was invalid and spending a strike toward locking it out, for a load spike
- **A reservation taken against the instance-wide login budget must be settled on every exit path.** `handleLogin` calls `admitCost` FIRST — before the per-IP lockout, the per-account lockout and the CAPTCHA check, deliberately, so an outbound CAPTCHA verification is inside the budget too — and every one of those can return without running a derivation. Holding the reservation on those returns made a request the server does NO work for more expensive to the budget than one it does: the bucket refills at `loginKDFDutyCycle` (0.2 s/s), so a caller already locked out drained it faster than it recovered for the price of an empty POST, and every legitimate sign-in on the instance — the admin's included — was answered 429 at the first check, indefinitely. The reservation is now held in a `loginBudget` value, settled exactly once by `chargeLoginKDF` (billing the true cost, or refunding a shed slot) or by `handleLogin`'s `defer budget.refund()`; `refund` is idempotent so the deferred call is inert once charged. Do not add a return between `admitCost` and the charge that bypasses the defer. `ipRateLimiter` additionally FLOORS the debt at one burst below zero in both `admitCost` and `settleCost`, so an unsettled reservation bounds recovery at `burst/refillPerSec` instead of growing without limit. Pinned by `TestRejectedLoginRefundsTheInstanceBudget`, `TestLockedOutFloodDoesNotDenySignInToEveryoneElse`, `TestBudgetIsSettledExactlyOnce`, `TestBucketDebtIsFloored`. **The `api` test binary stubs the budget's STOPWATCH, never its bucket** (`loginKDFBilledSeconds`, assigned once in `TestMain`). The budget meters measured seconds of derivation, and a measured second is the one quantity that cannot be honest there: `TestMain` also drops scrypt to 2^14, and `-race` then inflates what that cheap hash costs on the wall by a factor belonging to the machine rather than the code. Billing real time made the 3.0 s burst worth ~17 sign-ins on a laptop and 3 on a CI runner, so tests about MFA replay, lockout scoping and push approval failed there — and only there — on a 429 about CPU capacity that no part of their subject concerns. Billing a flat `loginKDFReserveSeconds` makes the burst worth exactly `loginRateBurst` sign-ins on every machine, which is what that constant already claims to be. Everything else stays live: real sizing, real refill, real shedding, and a test that drains the bucket gets the same 429 a caller would, so none of the four tests above can pass vacuously. Do NOT instead hand tests an un-drainable bucket — an absence-of-429 assertion then holds against a `handleLogin` with the refund deleted. `billMeasuredTime` is pinned by `TestProductionBillsTheMeasuredTime` and the stub's value by `TestTestBinaryBillsExactlyOneReserve`, because no other test in the package exercises the shipped oracle. A test that signs in more than `loginRateBurst` times against one server will be shed, correctly and deterministically; `lockOutAddress` is how the two flood tests get an address locked out without spending the burst to do it
- **`failureLockout` never evicts a live entry to stay under its cap; it SHEDS new keys instead.** Past `loginLockoutHardCap`, `tryAttempt` refuses keys the table has not seen (429) and sets `saturated`; keys already tracked proceed normally, so a flood cannot lock out users mid-accumulation. There used to be a second sweep stage that evicted locked entries to make room, and that was a lockout bypass with a price tag rather than a memory bound: an attacker wanting more guesses at one account pushed the table past the cap with rotating keys, and their target's cooldown was in the first tranche deleted — fifteen minutes became zero, repeatably. Shedding is fail-CLOSED; losing availability for unseen keys is visible and ends with the flood, whereas silently unlocking accounts is invisible and is what the flood is for. `logSaturatedLockouts` (on the session sweeper) reports it, because from outside a shed is indistinguishable from "login is broken". The sweep that remains reclaims only entries idle past `lockoutFor`, and keys off `lastSeen` NOT off "is this locked right now" — the latter deleted 1-of-3 and 2-of-3 progress and stopped the lockout engaging at all. Pinned by `TestFailureLockoutIsHardBounded`, `TestSaturatedTableStillServesKnownKeys`, `TestCrowdedTableDoesNotErasePartialStrikes`
- `users.Store`'s read cache is reached only through `withCachedUsers`, which passes the cached slice to a callback instead of returning it. The slice IS the cache's backing array, so a reader that retains, sorts or writes through it corrupts every subsequent request in the process; a callback makes that impossible to do by accident rather than forbidden by comment. `Get`/`GetByUsername`/`List` clone what they keep (`User.clone`, which deep-copies every field a plain struct copy would still share with the cache — currently `RecoveryCodesHash` and `PGPWrappedEnvelopes`). Mutators do not use it at all: a read-modify-write must start from disk inside the file lock (`readFileUnlocked`). `Get`/`GetByUsername` resolve through `withIndexedUsers` against id and normalized-username maps built alongside the cache, not by scanning: `api.currentUser` calls `Get` on every authenticated request, and `GetByUsername` ran `NormalizeUsername` over every stored username on every login attempt, so per-attempt cost grew with the size of the instance on the one endpoint that is deliberately expensive and reachable anonymously. The index stores POSITIONS, not `*User` — the slice aliases the cache — and is rebuilt only when the file's stat changes, by the same check that governs the cache
- `users.HashPassword` writes every new hash as Argon2id at `hashParams` (`password.DefaultParams()`, RFC 9106's second option: 64 MiB, t=3, p=4), not scrypt. `users.NeedsRehash` reports true for every `scrypt$` hash unconditionally (the format is retired) and for an Argon2id hash weaker than `hashParams` on any axis (memory, time, or threads); only a hash stronger on EVERY axis is left alone, so a 256 MiB hash at `t=1` is re-derived at the current parameters. It also refuses a hash whose costs are outside `password.Params.Validate`'s band, because that is a hash `password.Verify` calls malformed and an account that already cannot authenticate must not read as one due for an upgrade. There are two independent test hooks, for two different fixture needs: `users.SetHashCostForTest` lowers `hashCostN`, the cost `LegacyScryptHashForTest` mints legacy scrypt fixtures at (it does **not** affect `HashPassword`, which never reads `hashCostN`); `users.SetHashParamsForTest` lowers `hashParams` itself, the cost every real Argon2id hash is written and checked against. Call either only from `TestMain`, never mid-run. `internal/api` applies both overrides (four minutes of tests → forty seconds); tests whose subject *is* the cost opt back out via `withProductionHashCost`. The sequential-tests invariant that makes this safe is enforced by `TestNoTestInThisPackageCallsParallel`, not by a comment. `api.timingDummyHash` re-derives when `hashParams` changes so login-timing equalization cannot silently compare against the wrong figure
- **Timing equalization on the unauthenticated credential paths is a wall-clock FLOOR, not matched work.** `api.credentialTimingFloor` measures one legacy scrypt verification at `users.MeasureLegacyVerifyCost` (production: `ProductionScryptN`) and `settleCredentialTiming` pads every outcome of a credential check on `POST /api/auth/login` and CardDAV Basic auth to it — unknown username, inactive account, Argon2id account, not-yet-rehashed `scrypt$` account, right password and wrong. Matching work was correct only while one format existed at one cost: `timingDummyHash` is always Argon2id, a legacy account is checked by `verifyScryptHash`, and the ~7x gap between them enumerated accounts on an anonymous endpoint — permanently, for exactly the dormant accounts that never sign in to rehash. `equalizeLoginTiming` stays, and now equalizes SLOT CONTENTION rather than the clock; it no longer panics on `ErrKDFBusy`, it logs and skips, because the floor is what the disclosure rides on. Measure around the CHECK only: `loginKDFReserve`/`settleCost` meter derivation seconds, and billing the sleep would empty the instance bucket. The floor is cached against `users.HashCostN()`, which is also the test hook — `TestMain`'s `SetHashCostForTest` lowers it with no second override to keep in sync. Pinned by `TestLoginTimingDoesNotRevealUnknownUsernames` and `TestDAVAuthTimingDoesNotRevealUsernames`, both of which plant a `LegacyScryptHashForTest` fixture and bound the max/min spread at 1.5x; the old test compared two Argon2id accounts and could not fail on this
- The inbox wire format carries `bodyMode` (`"html"`/`"plain"`) alongside `body`, sourced from the MIME part the body was actually taken from (`imapadapter.clientBody`; `pgpmail.ParseContent` did the same before server-side PGP decryption was retired) and carried through `mailcache.Entry`. **Absent (`""`) means the server cannot know, and `clientBody` must return `""` — not `"plain"` — for an empty body**, or a confident answer gets stamped on a body that was never parsed and `mailcache.Store.Sync` preserves it forever. `bodyMode` describes the message the SERVER holds; for a client-protected account that is the ENVELOPE, and a `multipart/encrypted` envelope says nothing about the plaintext inside. The browser reads its own mode off the decrypted entity's `Content-Type` (`lib/mimeContent.ts`, held to `pgpmail.ParseContent` by the shared `testdata/mime-corpus.json`) and pairs body-with-mode in exactly one place (`pages/read/body.ts` `displayBody`). Clients must not re-derive the mode by inspecting bytes: `<user@example.com>` is plain text and treating it as markup deletes the address, while a tag allowlist calls `the <p> tag` markup and deletes that
- Usernames are validated by `users.ValidateUsername` at `Store.Create`: alphanumeric first character, then letters/digits/`.`/`_`/`-`, max 64. The rule exists because the CardDAV surface builds principal and address-book URLs out of the username and then guards access by comparing the first path segment back against it — `alice/bob` served its own owner a principal URL it then refused, and `..` produced paths outside the `/dav` mount. Existing accounts are not re-validated, so a pre-rule username keeps working
- Legacy `admin.env` is imported into `users.json` on first start (`users.LoadOrMigrate`), and legacy global data files are copied into the first admin's per-user dirs (`app/migrate.go`)
- Every bounded in-memory map in `api/` has an explicit sweep — sessions, MFA login challenges, the login/DAV/MFA/device lockouts, the single-use token set (pairing nonces and spent QR tokens), both cooldowns, the pickup store, and `deviceIndex`. `deviceIndex` was the last holdout and the one with attacker-influenced keys; `sweepDeviceIndex` rides `StartUserStoreSweeper` because it needs the same walk over every account's store, and it exempts in-flight reservations (`deviceReserving`) because those are precisely the entries with no disk row yet. **A maintenance pass walks every account's store with `userStoreForMaintenance`, never `userStore`** — the warming accessor stamps `userLastSeen`, and `sweepDeviceIndex` runs on the line before `sweepIdleUserStores`, so touching every user microseconds earlier meant the idle sweep could never evict anything and its eviction path was dead code. `rescanDeviceIndex` was corrected for this; its sibling was not, by the commit that claimed to fix it. "Swept lazily on access" is not a sweep: an entry nobody comes back for is never accessed. New per-request state that can be created by an unauthenticated (or merely password-holding) caller needs a sweeper wired in **both** `app.go` mode blocks
- Per-user data: IMAP credentials/tuning/notification prefs/label set/CardDAV app-password hash under `$CONFIG_DIR/users/<userID>/`; mailbox state (checkpoint, processed set, decisions, push subscriptions, native devices, pairing `subscriberId`, contacts, mail cache) under `$STATE_DIR/users/<userID>/`. Global: `config.yaml` (timezone, log level, scan interval, rate limits, redaction, the HOUSE label list, VAPID keys), root `$STATE_DIR/state.db` (AI-credits flag only)
- Contacts: per-user address book (`contacts/` package) synced two ways — a session-authenticated JSON CRUD API for the web UI, a real CardDAV surface (`/dav/{username}/contacts/`, HTTP Basic Auth against a separate app-specific password, not the login password) for native OS/CardDAV clients, and a per-device-credential-authenticated two-way JSON sync endpoint (`/api/contacts/sync`) mirroring the native push pull/pairing mechanism, for the companion mobile app. See [internal/contacts/AGENTS.md](internal/contacts/AGENTS.md)
- Mail cache: per-mailbox metadata cache (`mailcache/` package) backing `GET /api/inbox` — warmed opportunistically by the `processor/` poller's existing ~90s fetch (INBOX only) and by `api/`'s own live-fetch fallback, so the classic (no-`since`) response is usually served with zero IMAP calls, and a `since`-based delta mode avoids re-fetching bodies for already-seen messages. Not a permanent store like contacts — see [internal/mailcache/AGENTS.md](internal/mailcache/AGENTS.md)
- Anti-phishing: inbound mail that impersonates KyPost itself is flagged **in place** with the IMAP keyword `$Phishing` and recorded as a `flagged_phishing` decision (`processor/phish_scan.go`). Flagging never moves, archives, files to Junk, deletes, bounces, or re-marks a message — the mail stays in INBOX and stays unread. Detection is deterministic (kypost:// URIs, host-agnostic links to this app's own pairing/pickup paths, forged system-notice subjects) and is gated by real DKIM over the account's own domain, run **only** when the content check trips, so ordinary mail costs no DNS. The Ollama classifier is never consulted. `$Phishing` is deliberately **not** in `config.Labels.Allowlist`, so it never becomes an inbox tab. The clients refuse non-allowlisted URI schemes on their own, unconditionally — this server-side flag is advisory, which is why every step of it is best-effort
- **The attachment endpoints serve the message's OUTER MIME parts and nothing else, at exactly one IMAP fetch per request.** There is no server-side decrypt-and-re-index path: for a PGP/MIME message the outer part IS the armored ciphertext, the browser unwraps it and resolves indexes inside it. `serveAttachmentList` used to probe part 0 and `serveAttachmentDownload` used to re-probe on `ErrAttachmentNotFound`, both to feed `pgpInnerAttachments` — which, once server custody was retired, could never succeed: every return site of `decryptPGPPayload` sets `KeepPayload` or a non-empty `DecryptError`, and that function gated on exactly those. So each of those endpoints paid a second full `GetEmails` download and MIME parse (bounded only by `mailmsg.MaxInboundMessageBytes`) to ask a question guaranteed to answer "no". Neither `go vet` nor staticcheck's `unused` can see this, because the dead functions were called — `TestEncryptedAttachmentRequestsCostOneFetch` is what pins it instead. Restoring any such path means proving `decryptPGPPayload` can succeed first
- Contact photos (`api/contacts_photo.go`): 5 MiB per photo, 200 MiB per account, content-hashed filenames, reference-counted sweep. **Every content type in `contentTypeExt` must have a decoder registered by a blank import in that file** — the upload path gates on `image.DecodeConfig`, so an advertised type with no decoder behind it is rejected 100% of the time with "file is not a decodable image". `image/webp` was exactly that (Go's stdlib has no webp decoder as of 1.26) and has been removed; restoring it means adding `golang.org/x/image/webp`, not a map entry. **The FILENAME is content-hashed; the URL is not.** `GET /api/contacts/{id}/photo` is keyed by contact UID, so replacing or deleting a photo leaves the URL unchanged — which makes it ineligible for `immutable` (a browser then never revalidates, not even on an explicit reload, and paints a replaced or deleted photo for up to a year). It answers `private, no-cache`, which still costs one conditional request rather than a re-download because `http.ServeFile` emits `Last-Modified` and honours `If-Modified-Since`. A `?ref=` cache-buster is not the fix: the route is `withMailAuth`, so paired native devices build this URL themselves outside this repo. Only `assets/` (hashed filenames) is `immutable`
- Secrets (IMAP passwords) are encrypted at rest with the single master key `$SECRET_DIR/imap-config.key`
- Application logs use `ky-primitives/logging` JSON on stderr; `KY_LOG_LEVEL` defaults to info and invalid values refuse startup. The adapter retains redaction and declares a fixed field vocabulary; unknown fields are dropped and counted. `logging/vocabulary_test.go` harvests production call-site keys and fails if any is undeclared; keep log keys in snake_case. Supervisord captures/rotates stderr; no application-owned log files remain. Classifier diagnostics never include model text.
- Backups use `ky-primitives/recoveryclient` v0.5.1. `internal/backup/` owns collection, token sealing, locking and drill checks; the library owns capsule cryptography and transport. API mutations require admin session, CSRF and the current account credential. The daemon owns scheduling; ordinary HTTP requests get a 20-second shutdown grace, followed by a separate backup-only drain of up to 16 minutes. API tracking includes completion audit and prevents new detached runs once draining begins; the daemon separately waits for its scheduler. With `KYPOST_BULK_BACKUP_REPOSITORY`, mail databases go to restic and the capsule seals a manifest; see [internal/backup/AGENTS.md](internal/backup/AGENTS.md).


### Internal Package Layout

- **Per-user mailbox state is SQLite** (`STATE_DIR/users/<id>/state.db`), not JSON. `state.Store` owns processed-message ids, the decision audit log, the deferral ledger, native devices, web-push subscriptions, and the App Pull queue. `RecordProcessedDecision` writes the decision, the processed marker AND the deferral delete in one transaction: retiring a message ends its deferral, and putting that in the store is what stops a caller forgetting it. Every method reads and writes the database directly — there is no in-memory copy, no dirty flags, and no `fsutil.WithFileLock`, because SQLite's own WAL locking is what makes the api and daemon processes safe against each other. Two rules that are load-bearing rather than tuning:
  - the DSN sets `_txlock=immediate`. `database/sql`'s `Begin` issues a DEFERRED `BEGIN`, which cannot upgrade to a writer under contention and fails `SQLITE_BUSY_SNAPSHOT` (517) — `busy_timeout` does not retry an upgrade. Pinned by `TestConcurrentUpdateNotifyLatchFiresOnce`.
  - `state.Store` releases its handle on UNREACHABILITY, via the `runtime.AddCleanup` registered in `state.New` — **not** on cache eviction. `api.Server.sweepIdleUserStores` must only drop the map entry. The caches hand out bare pointers and release `userMu` before the caller is done, and `userLastSeen` records acquisition rather than release, so "idle" never means "unheld": closing at eviction severed the handle under long-running callers and their next query failed `sql: database is closed`. `Close()` remains, is idempotent, and is for callers that genuinely own the last reference. Pinned by `TestEvictedStoreStaysUsableForItsHolder`.

- **`state/schema.go`'s `schema` const migrates new TABLES, never new COLUMNS.** Every statement in it is `CREATE TABLE IF NOT EXISTS`, so on an existing install the `IF NOT EXISTS` fires and a column added to that const is never created — every query naming it then fails `no such column`, which on `native_devices` takes mail sync, contacts sync, App Pull and push MFA down together on upgrade, and only on upgrade, so a fresh-database test suite passes throughout. A new column goes in the const **and** in `additiveColumns`, which `openDB` applies via `ALTER TABLE ... ADD COLUMN` when `pragma_table_info` shows it missing; it needs a non-NULL `DEFAULT`, both because SQLite requires one for `NOT NULL` and because that default is what every existing row decodes as. Pinned by `TestEnrollmentColumnsAreAddedToAnExistingDatabase`, which builds the pre-migration table by hand — the only way to exercise an upgrade. **The probe and the `ALTER` run in ONE transaction**, because the api and daemon both open every `state.db` at startup: as two implicit transactions they are a check-then-act across processes, and on the first boot after an upgrade both see the column missing, one adds it, and the other fails `duplicate column name` — a SQL *logic* error, so neither `busy_timeout` nor `_txlock=immediate` retries it, and it reaches `log.Fatal`. The `Begin` takes the write lock up front, so the loser waits and then reads a pragma that already shows the column present. Table and column names are file-local constants, which is the only reason the `fmt.Sprintf` is safe; nothing enforces that but this note.
- **`upsertNativeDeviceTx` rebuilds the whole device row, so any field the device does not resend must be carried forward explicitly.** Both re-registration branches (by device id, and by push token + platform) do this for `mfa_approver` and, via `enrollmentState`, for the enrollment columns. A device re-registers on every app start and whenever its push token rotates, and it never resends its enrollment key — that is published once through `POST /api/pgp/device/enrollment-key` — so a missing carry-forward is not a rare race but an ordinary token refresh silently erasing the key mid-ceremony, leaving the browser sealing to a key that no longer exists. A new column on this table needs a line here or it is destroyed by the next registration. Two rules make the carry-forward hold by construction rather than by convention: the enrollment fields are **zeroed at the top of the function, before the branch**, so no caller can set them on any path (only `POST /api/pgp/device/enrollment-key` writes them, under the device's own credential), and the push-token branch carries `user_id` forward like every other preserved field — it did not, so a caller that omitted the owner blanked it.
- **`rules.ValidateRule` runs at every boundary a rule can enter through, including the one it is already inside.** JSON create, JSON update, Sieve import — and `rules.FilterRunnable` at both consumers (`processor`'s tick, `api`'s manual run), because `rules.json` is a plain file that predates the checks. It bounds the action count (20), the name and value sizes, the known action types, the visibility ordering above, and — for the `regex`/`matches` comparators — **compiles the pattern**. Compiling at the boundary is what bounds cost rather than shape: `maxConditionValueBytes` caps SOURCE length and `maxCompiledPatterns` caps the cache's ENTRY count, so neither sees that Go expands a bounded repeat and a 504-byte value compiles to a ~22 MiB program (`maxPatternProgramInsts` is the bound that does). An oversized pattern is **rejected, never merely left uncached** — an uncached pattern is recompiled per message, which trades memory exhaustion for CPU exhaustion. And an unevaluable condition must report *unevaluable*, not `false`: `matchesValue` returns `(matched, evaluable)` because collapsing the two let `Negate` invert a failed compile into "matches every message", so one mistyped character became a rule that swept the mailbox. Evaluation additionally carries its own wall-clock ceiling (`maxEvaluationBudget`) — `ctx` alone only cancels when the CLIENT disconnects, and an attacker holds the connection open. Each action is one IMAP round trip per matching message inside the size-1 instance-wide tick semaphore, so an unvalidated list was one authenticated user's rules deciding how long every other account waited for mail; an unknown action type was worse than useless, failing identically forever while classified as retryable. Mirrored — not replaced — in the frontend by `lib/ruleActions.ts`, which only decides what the builder lets a user compose.
- The other per-user stores (contacts, rules, groups, sendas, mailcache) and `users.json` are still JSON under `fsutil.WithFileLock`. They mutate on user action rather than per message, so they do not have the rewrite-per-event cost that moved `state.Store`.
- **No reader swallows a refresh-from-disk error. Every JSON-store reader returns it and every caller fails closed.** The in-memory slice behind each store is a cache of a file the api and daemon processes both write, so a failed re-read means this process does not know what the file says — and answering anyway is indistinguishable from a healthy read, indefinitely. There is no "decorative reader" exception: the classification was wrong in practice, because what a listing feeds is not visible from the listing. `contacts.Store.List` fed the recipient-key resolver (a storage fault landed a recipient in `withoutKeyEmails`, the bucket the send path offers the plaintext pickup fallback for) and the contact-photo sweep (an empty result means "nothing is referenced", so the sweep deleted every photo the user had); `groups.Store.List` fed `sanitizeGroupIDsForUser`, which writes its result onto the contact being saved, so an unreadable `groups.json` erased the user's group memberships. The stores under this rule: `contacts` (`List`, `Get`, `GetSelf`, `Search`, `ChangedSince`, `PGPKeyGeneration`), `groups` (`List`, `Get`), `sendas` (`List`, `ListVerified`, `Get`, `PendingNotExpired`, `FindVerifiedByEmail`), `rules` (`List`, `Get`), `mailcache` (`Snapshot`, `SyncContactKeyGeneration`), `wkdpublish` (`VerifiedDomains`), and `config.LoadUserSettings` via `UpdateUserSettings` (a parse failure is not a first run; starting from defaults reset the notification and content-preview privacy settings and then overwrote the file that would have shown what they were).
- **Failing closed is per-caller, and it is not always a 5xx.** Three shapes, in order of preference: refuse the operation (`GET /api/contacts`, the send path's recipient plan, the photo sweep, `handleInbox`'s warm-cache read); discard the derived trust instead of the request (`handleInbox` drops every cached signature verdict when `PGPKeyGeneration` cannot be confirmed, costing one body re-fetch per signed message and keeping mail readable); or answer with the empty set when empty is the safe answer (`boundSignerKeys` sends no keys, which can only produce "signed, but not by a key you hold" — never a green badge; `publishableAddressesAt` publishes nothing). What is never allowed is letting the error read as ordinary data: "no contact", "no key", "no groups" and "not verified" are all answers this codebase acts on.
- On first start after upgrade, `state.json`/`decisions.json` are imported into `state.db` in one transaction and renamed `.migrated` — never deleted. An unparseable file fails the open loudly rather than starting empty.

### Classification Loop (daemon mode)

- **Incoming encryption is per-user opt-in (`UserSettings.EncryptIncoming`, default false).** `processor/incoming_encryption.go` evaluates header rules and contact/embedding/LLM classification before unsigned public-key MIME replacement; it does not persist original-message sorter predictions for learning from encrypted replacements; the durable ciphertext-only job resumes before inbox scans, even after opt-out. Recoverable key/mailbox failures keep retrying; permanent per-message size/rule failures use the bounded deferral ledger, then record an explicit failure while preserving plaintext in IMAP. Feasibility and normalized rule-value validation precede classification and LLM quota admission. Older unsafe jobs finish with invalid actions skipped and a failure audit. Pending jobs reserve the fingerprint against destructive key writes; same-key rewrap and expired-key cleanup remain possible. `GET|PUT /api/pgp/incoming` is caller-only; writes need fresh account confirmation, and enablement needs a client-protected usable key, backup acknowledgment and current revision. The full wire/recovery contract lives in [../docs/E2E_PGP.md](../docs/E2E_PGP.md#incoming-mail-encryption-opt-in).

1. Poller fires on timer; lists active users from `users.json` and fans out over those with a stored IMAP config (bounded concurrency 4, per-user panic recovery)
2. Per user: fetch unread emails from their IMAP mailbox since their checkpoint
3. Scan each newly-seen message for KyPost self-impersonation and flag it with the `$Phishing` keyword if it does not authenticate to the account's own domain (`flagAppImpersonation`). Runs before every step below on purpose: a security verdict must not be rationed by the classifier rate limit, nor suppressed by a filter rule's `stop` action or a classifier outage
4. A PGP-encrypted message leaves the pipeline here: there is no readable body to classify (the poller never decrypts, and `Message.PGPEncrypted` is set precisely *because* no MIME part rendered), so `tagWithFallbackLabel` applies the account's fallback label, notifies, and records the decision — steps 5-8 never run. It is never labelled as encrypted; see the note at the skip in `poller.go` and in `SECURITY.md`. The same helper serves the auto-labeling-disabled path, so the two cannot drift apart in what they write
4b. Pre-sort (`presort.go`), after filter rules and before redaction. `tickUser` makes one `FetchHeaderFields` for the batch (pre-sort headers plus `rules.HeaderNames`, `TooLarge` UIDs excluded). If it fails while a rule tests a header, every message is held after the phishing scan and the tick fails; a UID the adapter skipped (byte budget) is held too. Header rules never run blind. With no header rules, pre-sort just skips its bulk check. A sender in the user's contacts (excluding `DiscoveryCreated` ones, which Autocrypt harvest adds from a stranger's first message) is tagged `Primary` through `tagWithLabel`, skipping the classifier and the rate limit; list/automated headers remove `Primary` from the allowlist sent to the classifier and from `SelectLabelFromText`. Headers only ever take `Primary` away; accounts without a `Primary` label are untouched. An unreadable contacts store turns the known-sender path off for the tick, never on
4c. Embedding sorter (`processor/sorter.go`, when `SetSorter` was given a model). The redacted, clamped sender/subject/body are embedded and the user's head predicts among the (pre-sort-narrowed) allowlist. At or above `EMBED_MIN_CONFIDENCE` its label is applied through the same keyword/decision path and steps 6-7 never run. `tickUser`'s rate pre-check makes the same call (memoised in `userCtx.guesses`) so confident mail never spends the LLM budget — the check stays BEFORE `handleMessage` because filter rules run there first and a rate deferral after them would re-run non-`stop` actions on the retry. Each user's head is retrained only when `sorter_generation`, the allowlist or the label descriptions change
5. Apply global redaction patterns to sender, subject, body
6. POST to Ollama `/api/generate` with the user's tuning prompt + redacted email text (one shared, serialized classifier client across all users)
7. Fuzzy-match Ollama response against the global label allowlist
8. Apply matched label as an IMAP keyword in the user's mailbox, then record the applied label with the message's vector (`RecordSorterPrediction`, best effort) so a later relabel can be learned
9. Send browser and native push notifications using the user's notification-mode gate (`none`, `all`, `keywords`) and the shared VAPID keys. An encrypted message's sender and subject are withheld from the native payload regardless of the user's Content Preview setting (`nativePushIncludesContent`) — that path is cleartext to the relay and to FCM/APNs. Web push is unaffected; RFC 8291 encrypts it to the browser's own subscription keys
10. Persist decision to the user's `state.db`
11. Advance the user's checkpoint — but only as far as the messages this tick actually retired. A message left unmarked on purpose (transient classifier failure, transient IMAP/state failure, spent rate budget, unreadable processed-set) holds the checkpoint below itself, because `ListUnreadInbox` only ever returns UIDs above it (`imap.ClampCheckpoint`)

**Retire or defer is one decision, and `tickUser` makes it once.** `shouldMarkProcessedOnError` answers it and the result is passed to `recordMessageFailure` rather than re-derived there — the checkpoint and the processed set must agree, and two copies of the predicate are how they stop agreeing.

- A `classifierErr` retires only when `isPermanentClassifierError` (bad input, credits exhausted). A transient outage defers.
- A `retryableErr` always defers. `handleMessage` wraps the failures a later tick can still complete: `applyKeywordsWithRetry` after its own retries, a failed rule action, and the `state.Store` writes that can hit `SQLITE_BUSY` past the busy timeout. **Wrapping is opt-in at the call site that knows the failure is an outage rather than a mistake.**
- `ParseError` retires one malformed MIME message with a failed decision, preserving raw mail and allowing later messages to proceed; it consumes no classifier slot and is not treated as oversized mail.
- Everything else retires. An unclassified error is one nothing has judged, and guessing "transient" means holding the checkpoint forever.
- **A failed rule action is not an applied rule.** `handleMessage` returns before writing any decision when `rules.ApplyOutcome` reports a failure. It previously appended the failure to the detail of an `applied` decision and — for a `stop` rule — retired the message in the same breath, so an IMAP reset during "archive and stop" left the mail in the inbox and an audit row claiming otherwise.
- **A deferral is only a retry if the retry query can still find the message.** The next tick looks for UNSEEN messages in INBOX above the held checkpoint, so `read`/`move`/`archive`/`spam`/`delete` take a message permanently out of reach. Two rules keep every deferral honest, and neither works alone: `rules.ApplyOutcome` stops at the first failed action (and at a cancelled context), and `rules.ValidateRule` allows at most one visibility-changing action per rule and requires it last (a trailing `stop` aside). Without both, "keyword fails, archive succeeds" archived the mail, dropped the keyword, recorded a failure, and left nothing that could ever come back for it.
- **Deferral is bounded, or it is not a retry.** Holding the checkpoint re-fetches a growing batch every tick, so `state.Store` counts attempts per message (`deferrals` table) and `tickUser` retires one that reaches `maxDeferralAttempts` (120, ~3h at the default interval), recording that it gave up. A store that cannot count attempts **fails closed**: the message stays deferred, the checkpoint stays below it, and `tickUser` returns an error so the outage reaches health. It used to retire instead, reasoning that an uncountable deferral is unbounded — but retiring is `RecordProcessedDecision` against the same store that just failed, so it bought no progress and paid in mail advanced past with neither label nor audit row. Pinned by `poller_tick_test.go`, which drives whole ticks through the `newMailClient` seam and asserts the processed set, the checkpoint and the audit log together — the defects above were each invisible to per-piece tests.

One failing mailbox never blocks other users; global health flips unhealthy only when every polled mailbox fails in the same tick.

## Work Guidance

- Enrollment-key publication atomically stores the device's `envelopeVersions` claim with its key, scoped by the device credential. Omitted/null claims reset to v2; registration cannot set claims and must carry them forward on both match paths. Additive SQLite/legacy JSON migration defaults to `[2]`; enrollment reset clears claims to `[2]`. Keep the validated `enrollmentEnvelopeVersions` field in owner device listings. This is codec metadata, not key-ownership or complete-ring acknowledgement. Exact bounds/defaults live in `docs/E2E_PGP.md`.
- **A device delivery is bound to the device's published key, the snapshot revision and the material generation, and the device's acknowledgement is checked against the same.** `users.Store.SetPGPDeviceEnvelope` is the only writer of `device:` slots (`SetPGPWrappedEnvelope` refuses the prefix): it parses the envelope's `{v, alg, epk, iv, ct}` framing without decrypting, accepts only `v: 3` on a converted account and `v: 2` on a legacy one, requires the expected fingerprint and, on a converted account, the revision and the current `materialGeneration` (`ErrPGPGenerationChanged` → 409 `pgpStateChanged`), and records `Version`, `MaterialGeneration`, `Fingerprint` and `EnrollmentKey` on the slot. `putDeviceEnvelope` first checks `enrollmentPublicKey` against the device's current published key and the version against its advertised list (409 `enrollmentChanged`), so a device that republished between SAS and upload gets nothing. `putDeviceEnvelope` then writes the delivered version, generation and fingerprint onto the device row, unconfirmed (`state.Store.RecordNativeDeviceDelivery`); `handlePGPDeviceEnrollmentState` can only confirm exactly that record (`ConfirmNativeDeviceEnrollment` matches all three in the UPDATE's WHERE), and only while it is still the account's current material and, while the slot lives, sealed to the key the device still publishes. **An acknowledgement confirms a delivery and never creates one**: everything a device can read on its own credential (bootstrap's generation and fingerprint, its own advertised versions) is deliberately not enough, so a device whose slot the owner deleted cannot re-open its own send gate; a bare boolean on a converted account is 409 `generationRequired`, because the legacy boolean is never proof of v3 enrollment. `false` and `ClearDeviceEnrollments` forget them; registration carries them forward on both match paths. `requireCurrentGeneration` gates `POST /api/mail/send-pgp`: a converted account must assert the current `materialGeneration` (409 `pgpStateChanged`) and a device caller (`AuthContext.DeviceID`, set by `resolveMailAuthContext`) must also be enrolled at it (409 `reenrollmentRequired`). Legacy accounts are not gated. `handlePGPDeleteEnvelopeSlot` clears the device's enrollment record with its slot (`clearDeviceEnrollment`), so removing a sealing stops that device's sends until it enrolls again; registration zeroes the three columns like their siblings so a device can never assert them. Nothing here merges rings or erases history

- `users.Store.CommitPGPKeyring` is internal only until browser recovery/native gates pass. Commit complete password/recovery envelopes, public identity, inventories and optional derived credential under the existing revision/file lock. Never shrink history (16 primaries/256 total fingerprints; 128 KiB per envelope); increment material generation only on inventory growth after initial generation 1. Conversion/growth clears device slots. Retirement requires a new usable encryption key; same-active public packet edits are refused. Metadata is consistency information, not proof of opaque contents. Snapshot APIs expose `keyring`; converted records require revision guards and reject legacy writes with `keyringUpgradeRequired`. Admin reset and derived-auth forced completion preserve opaque material; legacy plaintext forced completion is refused on converted accounts; ordinary credential changes require `keyringVersion: 1` and a complete password rewrap via `ChangeKeyringPassword`. This reuses the password mutation, preserving public/recovery metadata, including absent recovery slots. Bind the request revision to the credential-verification snapshot and check it again under the disk lock. No conversion or forced-reset rewrap is allowed.

- PGP identity, wrapped-key, bootstrap and slot responses include `pgpRevision` from their own user snapshot; mutation responses return the committed revision. Client identity/rewrap, slot PUT/DELETE, identity DELETE and password change accept `expectedRevision`; mismatch returns 409 with `pgpStateChanged: true`, without committing credentials or envelopes. Browser writers supply snapshot-bound revisions; converted accounts require guards and reject legacy single-key writers. `GET /api/auth/password` returns only the caller’s revision/protection/wrapped envelope/forced-change flag with no-store. Forced-change snapshots withhold the envelope; completing the forced change preserves it for later recovery. Do not exempt full PGP bootstrap for temporary credentials.

- `RewrapPGPKeyring` and `/identity/rewrap` with `keyringVersion: 1` repair only password ciphertext on existing v1 client rings. Require derived auth, no forced change, explicit fingerprint and revision. Bind the pre-step-up snapshot to that revision, then compare under the store lock. Preserve all credentials/public/recovery metadata; legacy rewrap still rejects rings.

- `SetPGPKeyringRecovery` permits only the recovery slot on existing v1 client rings with derived auth, no forced change, fingerprint and revision. Versioned slot PUT binds the pre-step-up snapshot revision and checks it under the disk lock; never use it for device enrollment. Preserve password ciphertext, credentials, public identity, inventory and material generation. Body bound 384 KiB; stored envelope bound 128 KiB.

- Recovery slot PUT and private-key rewrap accept optional `expectedFingerprint` for older-client compatibility. When supplied, compare it inside `users.Store.mutate` before writing; stale identity material gets 409 without mutation. The browser recovery paths always supply it. Slot GET returns public identity metadata and ciphertext from one user snapshot. The browser sends no recovery secret or plaintext key; handlers treat envelopes as opaque and never log their contents.

- Build: `cd backend && go build -buildvcs=false ./...`
- Test: `cd backend && go test ./...` (CI runs `-race`; several stores are shared across the api and poller goroutines in `all` mode)
- **A guard belongs at the shared sink, not at the call sites that remembered it.** This is the repo's most repeated defect and every instance looked identical: the guard existed, worked, and covered a strict subset of what needed it — `checkVCardFolding` on 1 of 3 vCard parse paths, verdict invalidation on 3 of 11 contact writers, `maxRecipientsPerSend` on 2 of 4 handlers running the same per-address contacts scan, `accountWriteLimiter` on 1 of 4 auth wrappers. Adding the missing call site fixes the report; moving the guard fixes the class. Where a sink cannot be shared because the code is in a dependency (go-webdav decodes vCard and PROPFIND itself), wrap the boundary instead — pre-scan and replace `r.Body`, or bound the transport — so a later call site inherits it. `pinPGPKeyFingerprint` inside `applyUpsertLocked` and the contact-photo quota inside its storage helper are the pattern done right
- **A verdict derived from another store records the generation it was derived under.** `mailcache` verdicts carry `ContactKeyGen`; the contacts store bumps `PGPKeyGeneration` when key material *or the address set* changes, and the inbox read path drops mismatches. Handler-level invalidation could not work here at all — three of the eleven contact writers are the daemon's Autocrypt writes, in a different process with no `*http.Request` — and it also missed address-narrowing, which changes what a key is an anchor for without changing its bytes. A number persisted beside the data is what both processes can see
- Keep adapter packages free of direct state mutation; they communicate via interfaces and channels defined in `processor/`
- PII redaction must be applied before any text is sent to Ollama — and before it is embedded by the sorter
- **The embedding sorter learns from the user and from nothing else.** Training data is the shipped fictional seeds, the user's label descriptions, and `sorter_corrections` — rows written only when a message the sorter (or LLM) labelled is relabelled by the user. LLM answers are never trained on: the "recent decisions" few-shot block was removed from the prompt as a stored-injection surface that recycled the model's own answers, and a training set is the same surface. Both relabel paths (`POST /api/inbox/actions` `label`, and keyword changes seen by `mailcache.Store.Sync` in `serveInbox`) end in `state.Store.RecordSorterCorrection`, which is the one place that decides whether a relabel is a lesson: a prediction must exist, its `check_hash` (sha256 of the IMAP adapter's sender NUL subject) must match so a reused UID teaches nothing, and relabelling back to the predicted label withdraws the correction. The sorter tables hold vectors, labels and hashes — no correspondence text — pinned by `state/sorter_test.go`
- User-scoped filesystem paths must pass user IDs through `fsutil.SafePathComponent`; malformed or legacy IDs must never become path components that can escape the configured users directory.
- The shared Logger redacts sensitive key/value fields before writing structured logs; pairing-secret failures must log only the safe remediation message, never secret-store paths or raw error text
- **Correspondence metadata never reaches application logs.** `GET /api/logs` serves captured logs to any admin, and an admin has no mailbox access to other users. The forbidden field list is machine-checked by `log_privacy_test.go` in both `api/` and `processor/` — it names `sender`, `subject`, `body`, `snippet` and `recipient`, and a field missing from it is simply not checked, which is how four send-failure lines came to log recipient addresses. Log an index or a count instead
- Do not add dependencies outside the go.mod without explicit approval
- **Cutting a release**: bump `serverVersion` in `internal/api/server_version.go` AND `frontend/package.json` (plus its lockfile) to the same value, in the same commit as the tag, add the release notes to `CHANGELOG.md`, and publish the GitHub release with a dotted-numeric tag (`v0.2.0`, not `v0.2-alpha`). `release-image.yml` now enforces the agreement rather than trusting it: it refuses to publish a tag that disagrees with either version source, and refuses a commit CI never passed. It then publishes the immutable `0.2.0` image, attests it, verifies the attestation, and only then promotes that exact digest to `stable` — never backward, and one release at a time. The host updater resolves stable to a digest and verifies the GitHub attestation before deployment. Every install polls this repo's releases hourly, emails its admin once per newly-seen release, and shows the cached result in Settings; a tag that is not dotted-numeric fails the comparison closed and no one is told, and a `serverVersion` left behind mails everyone about a release they are already running

The sorter parity test and the poller's hybrid tests skip unless `EMBED_MODEL_DIR` points at the pinned model; `ci-backend-other` downloads it using the Dockerfile's `EMBED_*` ARG pins, so set it locally too or those tests prove nothing. The `-timeout` is not optional: `internal/api` alone exceeds Go's default 600s under `-race`, which is why CI splits it into its own job and passes `-timeout=20m`. Running plain `go test -race ./...` locally reports a timeout that CI would not see

- `GOTOOLCHAIN=go1.26.9 go test -race ./internal/sso ./internal/api -run '^TestReleaseFloor' -count=1` checks monotonic durable release floors, the refusal rule, snapshot validation, webhook refusal of stale activations while queued deletions apply, direct allocation refusal, unchanged active rows passing, and the worker quietly refusing administrator provisioning, unpublished allocation and reallocation of a repaired account while the disable path converges.

- `GOTOOLCHAIN=go1.26.9 go test -race ./internal/api -run '^TestNativeRecoveryEvidenceCannotApplyDirectoryState$' -count=1` checks signed recovery-purpose refusal, exact account/lifecycle/hold preservation and ordinary sync continuity. It does not qualify evidence consumption or restore release.

- Actual `TestNativeReceivingMaddyRuntime` modes also join accepted/imported mail to the production HTTPS API with synthetic pre-registered device credentials: both frozen owners get full native snapshots, exact binary attachments and bodies, while foreign-owner references are refused. Registration, full image API/daemon deployment, client UI, public-domain delivery and PGP remain separate checks.
